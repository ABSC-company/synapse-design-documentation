# 1.9.5. Warehouses Page

## Спецификация страницы интерфейса

* **Название страницы:** Склады
* **Модуль:** Управление клиникой (Clinic Management Module)
* **Владеющие бэкенд-модули:** Structure Module (кабинеты и их расположение на карте), Warehouse Module (справочник складов)
* **Тип страницы:** Реестр + интерактивная 2D-карта этажа
* **Основные роли:** Администратор клиники (`STRUCTURE_ROOM_*`, `WAREHOUSE_STORAGE_MANAGE`)
* **Маршрут:** `/clinic-management/warehouses`
* **Статус документа:** Актуализировано (`room_id` — теперь собственное поле склада, валидируется бэкендом: существование кабинета и эксклюзивность проверяются на сервере, см. §4.15a `WarehouseModule.md`)

> Общие паттерны карты — см. `1.9.0. Clinic Management Overview`. Бэкенд-контракт — `StructureModule.md` §5.8, §8.7, §14.7 (кабинеты — не стенды, см. ниже); `WarehouseModule.md` §4.15, §4.15a, §8.4, §12.6 (справочник складов и их размещение — тот же API, что использует `1.7.6. Storages Page`, плюс `room_id`).

## Важное отличие от `1.9.4`/`1.9.7`: склад размещается в кабинете, а не на стенде

Склад — физическое помещение (кладовая, аптечный склад отделения), а не стойка/островок в коридоре. Новая сущность **стенд** (`StructureModule.md` §5.10), добавленная в эту ревизию, по определению предназначена только для касс и окон ресепшена (см. бэкенд-документацию Structure Module — стенд явно описан как «не полноценная комната»). Поэтому размещение склада на карте использует уже существующую сущность **кабинет** (`rooms`, `StructureModule.md` §5.8), а не стенд — отдельного бэкенд-фикса для этой страницы не потребовалось, механизм уже был полностью реализован для `1.6.2`.

С помощью страницы пользователь может:

1. Просматривать список складов клиники (справочник — тот же, что `1.7.6`) с указанием кабинета размещения (или «не размещён»).
2. Создавать/редактировать/удалять склад (та же форма, что `1.7.6`: название, тип основной/потребительский, отдел, родительский склад, ответственный).
3. Открывать 2D-карту этажа и привязывать склад к конкретному кабинету.
4. Снимать привязку склада к кабинету.

## User Flows / Task Flows

### Flow 1. Просмотр реестра

1. Таблица: название склада, тип (основной/потребительский), отдел, кабинет размещения (или «Не размещён»).
2. Клик по размещённому складу — карта центрируется на его кабинете.

### Flow 2. CRUD склада (справочник)

1. Полностью повторяет `1.7.6` Flow 1–2 (создание/удаление, включая блокировку удаления склада с активными кодами маркировки/незавершёнными запросами, `409 ENTITY_HAS_DEPENDENCIES`).
2. Создание не требует немедленной привязки к кабинету — склад может существовать без физического размещения (например, филиал ещё не разметил карту).

### Flow 3. Привязка склада к кабинету

1. Пользователь выбирает этаж, видит план с кабинетами.
2. Кабинеты, уже занятые под какой-либо склад, — подписаны названием склада; свободные — нейтральные; кабинеты с иным назначением (`rooms.type = laboratory`/`instrumental`, занятые под приём) — визуально доступны для выбора наравне со `service`, так как Structure Module не ограничивает `type` кабинета для целей размещения склада (это выбор конкретной клиники, кабинет может совмещать функции).
3. Клик по нераспределённому складу в боковой панели → режим «Выберите кабинет на карте».
4. Клик по кабинету → подтверждение → `PATCH /api/v1/warehouse/storages/{id}` с `{ room_id }` (`WarehouseModule.md` §4.15a, §12.6) — модуль сам проверяет существование кабинета и эксклюзивность через Structure Module, отдельного вызова к Structure Module с фронта не требуется; `404 ROOM_NOT_FOUND`; `409 ROOM_ALREADY_ASSIGNED` — кабинет уже занят другим складом. Кабинет на карте подписывается названием склада.

### Flow 4. Снятие привязки

1. «Снять с кабинета» → подтверждающий диалог → `PATCH /api/v1/warehouse/storages/{id}` с `{ room_id: null }`; сам склад и его остатки не затрагиваются.

### Flow 5. Кабинет пропал с карты (`orphaned`)

1. Аналогично Flow 5 страницы `1.9.4`: кабинет, чей `path` не найден при повторной загрузке SVG, переходит в `status: "orphaned"` (`StructureModule.md` §5.8) — не удаляется.
2. Склад, привязанный к такому кабинету, показывается в реестре с предупреждающим бейджем «Кабинет не на карте».

## Состояния и edge cases

| Состояние | Ожидаемое поведение |
|---|---|
| loading | Skeleton списка / карты |
| empty | Складов нет — «Склады не созданы» + «+ Добавить склад» |
| error | Toast при сбое CRUD/привязки; ошибка загрузки карты — блок ошибки + «Повторить» |
| permissions | CRUD склада, включая привязку к кабинету — `WAREHOUSE_STORAGE_MANAGE`; просмотр карты кабинетов — `STRUCTURE_ROOM_GET` |

### Edge cases

1. Привязка двух складов к одному кабинету — отклоняется на бэкенде (`409 ROOM_ALREADY_ASSIGNED`, `WarehouseModule.md` §4.15a); клиентская фильтрация свободных кабинетов на карте — только для быстрой обратной связи, финальная защита от гонки — на сервере.
2. Удаление кабинета через `1.6.2`, пока к нему привязан склад, — блокируется на бэкенде, только если у кабинета есть рабочие места (`StructureModule.md` §14.7) — привязка склада сама по себе это не отслеживает; при удалении кабинета склад переходит в состояние Flow 5.

## Зависимости и ограничения

### API

1. `GET /warehouse/storages`, `POST/PATCH/DELETE /warehouse/storages` — справочник складов, включая размещение (`room_id`, `WarehouseModule.md` §4.15a, §12.6) — тот же контракт, что `1.7.6`, расширенный полем `room_id`.
2. `GET /api/v1/structure/rooms/{branch_id}` — кабинеты для привязки (`StructureModule.md` §8.7, §14.9a).
3. Сама привязка выполняется через Warehouse Module (п. 1), не напрямую через Structure Module.

### Роли и права

| Действие | Право |
|---|---|
| Просмотр реестра складов | `WAREHOUSE_STORAGE_GET` |
| CRUD склада, включая привязку/снятие кабинета | `WAREHOUSE_STORAGE_MANAGE` |
| Просмотр карты и кабинетов (только для отрисовки — привязку валидирует сам Warehouse Module) | `STRUCTURE_ROOM_GET` (3430) |

## Acceptance criteria

1. Реестр складов показывает кабинет размещения или «не размещён».
2. CRUD склада полностью повторяет `1.7.6`, без дублирования логики на этой странице.
3. Привязка и снятие склада с кабинета выполняется через карту этажа с явным подтверждением.
4. Кабинет, ставший `orphaned`, отражается в реестре склада как «Кабинет не на карте», без потери самого склада.
5. Действия скрыты/задизейблены без соответствующих прав.
6. Состояния empty/loading/error/permissions обработаны.
