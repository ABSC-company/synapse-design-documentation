# 1.9.6. Services Catalog Page

## Спецификация страницы интерфейса

* **Название страницы:** Каталог услуг
* **Модуль:** Управление клиникой (Clinic Management Module)
* **Владеющий бэкенд-модуль:** Services Module
* **Тип страницы:** Реестр + карточка услуги/пакета
* **Основные роли:** Администратор клиники (`SERVICES_*`, `SERVICE_PACKAGE_*`)
* **Маршрут:** `/clinic-management/services`
* **Статус документа:** Актуализировано

> Общие паттерны — см. `1.9.0. Clinic Management Overview`. Бэкенд-контракт — `ServicesModule.md` §4 (доменная модель), §8 (REST API), §9 (права).

---

## Назначение страницы и сценарии использования

Единая точка управления каталогом всех оказываемых клиникой услуг и продаваемых товаров, их категориями, расходниками и пакетами услуг. Каталог — анемичная модель (справочник), используемая при букинге (Booking Module) и выставлении счетов (Payments Module); эта страница — единственное место его редактирования.

С помощью страницы пользователь может:

1. Просматривать каталог услуг/товаров с категориями и статусом (`active`/`discontinued`).
2. Создавать/редактировать услугу: название, описание, цена, единица измерения, длительность, тип (`consultation`/`laboratory`/`instrumental`), код ИКПУ.
3. Управлять расходниками услуги (привязка товаров склада и норм расхода).
4. Управлять категориями услуг.
5. Снимать услугу с продажи (`discontinued`) — полное удаление недоступно принципиально.
6. Создавать/редактировать пакеты услуг и их состав.

## User Flows / Task Flows

### Flow 1. Создание услуги

1. «+ Добавить услугу» → форма: название, описание, цена, количество за эту цену, единица измерения (`service`/`procedure`/`minute`), длительность (минуты), тип (`consultation`/`laboratory`/`instrumental`), ИКПУ (17 цифр, обязателен, с форматной валидацией на клиенте).
2. Категории — множественный select из справочника (`1.9.6`, блок категорий, Flow 4).
3. Сохранение → `POST /api/v1/services`.
4. Подсказка при выборе типа `laboratory`/`instrumental`: «Эта услуга бронируется на процедурный/лабораторный кабинет, а не на конкретного врача» — тип определяет, к чему привязывается визит при букинге (`ServicesModule.md` §4.1), явное пояснение снижает риск ошибочного выбора при заведении новой услуги.

### Flow 2. Расходники услуги

1. Карточка услуги → блок «Расходники» (виден, только если `have_consumables` включён в форме услуги).
2. «+ Добавить расходник» → select товара из каталога Warehouse Module (`remote`-подгрузка) + количество расхода на одну реализацию.
3. Наличие расходников на складе не проверяется этой формой — проверка происходит в момент букинга (`ServicesAvailabilityService.checkAvailability`, `ServicesModule.md` §5.1); здесь только состав нормы расхода.

### Flow 3. Снятие услуги с продажи

1. «Снять с продажи» (не «Удалить» — формулировка кнопки явно отражает необратимость направления перехода статуса).
2. Подтверждающий диалог: «Услуга станет недоступна для новых записей; исторические счета и визиты не изменятся».
3. `DELETE /api/v1/services/{id}` → перевод в `discontinued`. Обратный переход не предусмотрен — восстановление возможно только созданием новой карточки услуги (об этом явно сказано в диалоге).

### Flow 4. Категории услуг

1. Отдельная вкладка/боковая панель «Категории» — простой CRUD (название, описание).
2. Удаление категории, назначенной услугам, — снимает привязку у этих услуг (не удаляет сами услуги); подтверждающий диалог показывает число затронутых услуг.

### Flow 5. Пакеты услуг

1. Вкладка «Пакеты» — отдельный реестр: название, цена, срок действия (дней, опционально — бессрочный, если не указан), статус.
2. Карточка пакета → блок «Состав»: список услуг с количеством каждой в пакете (`service_package_items`), добавление/изменение/удаление позиций.
3. Снятие пакета с продажи — тот же паттерн, что Flow 3 (`discontinued`, необратимо на UI).

## Визуал: High-Fidelity mockups

1. Вкладки «Услуги / Пакеты / Категории» — единый верхний переключатель, без ухода на отдельные маршруты (контент меняется внутри страницы).
2. Тип услуги (`consultation`/`laboratory`/`instrumental`) — небольшой иконочный бейдж рядом с ценой в списке, для быстрого визуального сканирования при большом каталоге.
3. Услуги в статусе `discontinued` — визуально приглушены (пониженный контраст строки) и по умолчанию скрыты фильтром «Активные», без явного включения показа архивных.

## Состояния и edge cases

| Состояние | Ожидаемое поведение |
|---|---|
| loading | Skeleton таблицы/карточки |
| empty | Услуг нет — «Каталог пуст» + «+ Добавить услугу» |
| error | Toast при сбое сохранения; форма не сбрасывается |
| permissions | `SERVICES_GET`/`SERVICE_PACKAGE_GET` — просмотр; операции — по своим правам ниже |

### Edge cases

1. Услуга без ИКПУ — форма блокирует сохранение с инлайн-ошибкой (обязателен для всех услуг/товаров, участвующих в счетах, `ServicesModule.md` §10).
2. Изменение цены/названия уже проданной услуги — не влияет на исторические счета и снимки пакетов (`invoice_items`, `package_snapshot` хранят снимок на момент продажи) — предупреждение об этом не требуется на UI, так как поведение ожидаемо и безопасно для истории.
3. Букинг услуги при нехватке расходников — разрешён или запрещён глобальной настройкой Management Module (`1.9.1`, раздел Services) — эта страница только формирует состав расходников, саму настройку не дублирует.
4. Попытка снять с продажи услугу, входящую в активный пакет, — не блокируется отдельно (пакет хранит собственный неизменяемый снимок состава при продаже), интерфейс не требует дополнительного предупреждения сверх стандартного диалога Flow 3.

## Interaction & Animation

1. Переключение вкладок «Услуги/Пакеты/Категории» — мгновенный фильтр контента без перезагрузки, тот же паттерн, что вкладки в `1.7.6`.
2. Карточка услуги/пакета — slide-in справа.
3. Добавление/удаление расходника или позиции пакета — строка списка появляется/исчезает с fade, без перерисовки всей карточки.

## Зависимости и ограничения

### API

1. `POST/GET/PATCH/DELETE /api/v1/services` — CRUD/снятие услуги.
2. `POST/PATCH/DELETE /api/v1/services/{id}/consumables` — расходники.
3. `POST/PATCH/DELETE /api/v1/services/categories`, `POST/DELETE /api/v1/services/{id}/categories` — категории.
4. `POST/GET/PATCH/DELETE /api/v1/services/packages`, `POST/PATCH/DELETE /api/v1/services/packages/{id}/items` — пакеты и их состав.
5. Товары для расходников (Flow 2) — `remote`-подгрузка из Warehouse Module.

### Роли и права

| Действие | Право |
|---|---|
| Просмотр каталога | `SERVICES_GET` (9001) |
| Создание услуги | `SERVICES_CREATE` (9000) |
| Изменение услуги | `SERVICES_UPDATE` (9002) |
| Снятие с продажи | `SERVICES_STATUS_UPDATE` (9003) |
| Расходники | `SERVICES_CONSUMABLE_MANAGE` (9010) |
| Категории | `SERVICES_CATEGORY_MANAGE` (9020) |
| Пакеты — создание/просмотр/изменение | `SERVICE_PACKAGE_CREATE` (9100) / `SERVICE_PACKAGE_GET` (9101) / `SERVICE_PACKAGE_UPDATE` (9102) |
| Состав пакета | `SERVICE_PACKAGE_ITEM_MANAGE` (9110) |
| Полный доступ | `SERVICES_MANAGE` (9900) |

> Продажа пакета пациенту (`SERVICE_PACKAGE_SELL`, 9120) — операционное действие, выполняется в ЭМК/регистратуре, не на этой странице.

## Acceptance criteria

1. Каталог поддерживает полный CRUD услуг (кроме физического удаления — только снятие с продажи), расходников, категорий и пакетов.
2. ИКПУ обязателен и валидируется по формату при сохранении услуги.
3. Тип услуги явно поясняется пользователю в форме создания (влияет на букинг — врач vs. кабинет).
4. Снятие с продажи — необратимое на UI действие с явным предупреждающим диалогом; архивные услуги скрыты фильтром по умолчанию.
5. Действия скрыты/задизейблены без соответствующих прав.
6. Состояния empty/loading/error обработаны.
