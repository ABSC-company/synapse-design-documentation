# 1.9.2. Roles and Permissions Page

## Спецификация страницы интерфейса

* **Название страницы:** Роли и права
* **Модуль:** Управление клиникой (Clinic Management Module)
* **Владеющий бэкенд-модуль:** Auth Module
* **Тип страницы:** Реестр + форма-конструктор роли
* **Основные роли:** Администратор клиники (`AUTH_ROLE_*`)
* **Маршрут:** `/clinic-management/roles`
* **Статус документа:** Актуализировано

> Общие паттерны — см. `1.9.0. Clinic Management Overview`. Бэкенд-контракт — `AuthModule.md` §6.2 (Roles API), §7.2.3 (каталог прав ролей).

---

## Назначение страницы и сценарии использования

Создание, изменение и удаление ролей системы — именованных наборов прав, которые затем назначаются сотрудникам на странице `1.9.3`. Роль в Synapse — плоский массив числовых кодов прав (`roles.permissions`, `AuthModule.md` §3.2), без встроенной иерархии ролей; страница визуализирует этот массив как матрицу, сгруппированную по модулям, для читаемости.

С помощью страницы пользователь может:

1. Просматривать список ролей: название, описание, число назначенных сотрудников, признак привилегированной роли; искать по названию и листать страницы (ролей может быть много).
2. Создавать роль — название, описание, набор прав.
3. Редактировать состав прав существующей роли.
4. Удалять роль.
5. Искать право по названию внутри матрицы и по модулю.

## User Flows / Task Flows

### Flow 1. Создание роли

1. «+ Создать роль» → модаль/форма: «Название» (обязательно, уникально), «Описание» (опционально).
2. Матрица прав: список модулей (каждый — сворачиваемая группа), внутри — чекбоксы отдельных прав с человекочитаемым названием и описанием на языке интерфейса (названия берутся из справочника прав приложения).
3. Поиск по матрице — фильтрует чекбоксы по названию права, автоматически разворачивая группы с совпадениями.
4. Сохранение — роль создаётся и появляется в списке.
5. Конфликт имени — `409`, инлайн-ошибка на поле «Название».

### Flow 2. Редактирование прав существующей роли

1. Клик по роли в списке → открывается та же форма-конструктор, предзаполненная текущим составом.
2. Перед показом формы — предупреждающий блок «Роль назначена N сотрудникам» (если N > 0), чтобы администратор понимал масштаб последствий до того, как начнёт снимать права.
3. Сохранение — изменения применяются всем пользователям с этой ролью немедленно; у онлайн-сотрудников меню и кнопки обновляются сразу, без перелогина.

### Flow 3. Удаление роли

1. «Удалить» → подтверждающий диалог с явным списком последствий: «Роль будет снята у N сотрудников» (при N > 0 — усиленное предупреждение, а не то же самое окно, что для роли без назначений).
2. Подтверждение — роль удаляется, права пересчитываются у затронутых сотрудников.
3. Массовое удаление — выбор нескольких ролей чекбоксами; выбор сохраняется при переходе между страницами списка.

### Flow 4. Привилегированные роли и права

1. Роль, в составе которой есть привилегированное право (полный доступ к модулю, управление ролями и пользователями и т.п.), в списке помечена бейджем «Привилегированная».
2. В матрице привилегированные права выделены; если у текущего пользователя нет такого права (или полного права управления настройками), чекбокс неактивен с подсказкой «Недостаточно прав для выдачи привилегированных прав».
3. Роль, которую текущий пользователь изменять не вправе, открывается только на просмотр: кнопка «Сохранить» скрыта, ✏ и 🗑 в списке неактивны с подсказкой.
4. Если система всё же отклонила сохранение из-за привилегированных прав, показывается сообщение, а в матрице отмечаются проблемные права.

## Визуал: High-Fidelity mockups

1. Матрица прав — сворачиваемые группы по модулю (аккордеон), группа с активным поиском авто-разворачивается.
2. Управляющее право модуля (`*_MANAGE`) визуально выделено (например, жирным/отдельной строкой над остальными правами группы) — его включение по смыслу перекрывает остальные права модуля, но UI не снимает и не скрывает остальные чекбоксы автоматически (соответствие бэкенду, где `permissions` — плоский список без вычисляемых зависимостей).
3. Строка привилегированной роли — бейдж «Привилегированная»; если пользователь изменять роль не вправе, ✏ и 🗑 неактивны (подсказка при наведении).

## Состояния и edge cases

| Состояние | Ожидаемое поведение |
|---|---|
| loading | Skeleton списка ролей / формы при редактировании |
| empty | Ролей нет — «Роли не созданы» + «+ Создать роль» (без роли ни один новый сотрудник не получит доступ, см. `1.9.3`) |
| error | Toast при сбое сохранения/удаления, форма не закрывается |
| permissions | Список ролей — `AUTH_ROLE_READ`; создание/изменение/удаление скрыты без соответствующих прав |

### Edge cases

1. Попытка удалить роль, назначенную хотя бы одному сотруднику, не блокируется, но UI обязан предупредить явно (Flow 3, п. 1) — тихое удаление недопустимо.
2. Права матрицы могут расти по мере подключения новых модулей — список модулей и прав не хардкодится компонентом, а строится по справочнику кодов прав, обновляемому вместе с релизами бэкенда.
3. Матрица потенциально длинная (много модулей × много прав) — сворачивание групп и поиск обязательны с первой версии экрана, а не как доработка «когда данных станет много».
4. Массовое удаление нескольких ролей — единый подтверждающий диалог суммирует общее число затронутых сотрудников по всем выбранным ролям, в том числе выбранным на разных страницах.
5. Поиск не нашёл ролей — «Ничего не найдено» и кнопка сброса поиска.
6. В набор роли попало право, которое приложение не знает (приложение старее сервера) — оно показывается как «Право {код}» без названия и не снимается автоматически.

## Interaction & Animation

1. Раскрытие/сворачивание группы модуля в матрице — плавный accordion, 150–200ms.
2. Поиск — подсветка совпадения в названии права, авто-скролл к первой совпавшей группе.
3. Модаль создания/редактирования — fade+scale, идентично паттерну модалей в остальных модулях.

---

## Зависимости и ограничения

### Справочник кодов прав для матрицы

Матрица строится по справочнику прав приложения — полному зеркалу реестра прав системы: коды, группировка по модулям, признаки «привилегированное» и «управляющее» совпадают с серверными, названия и описания — на языке интерфейса. Справочник обновляется вместе с релизом приложения; запрашивать его у сервера не нужно.

## Acceptance criteria

1. Список ролей отображает название, описание, число назначенных сотрудников, признак привилегированной роли; поддерживает поиск по названию и постраничный просмотр.
2. Матрица прав сгруппирована по модулю, поддерживает сворачивание групп и поиск по названию права с первой версии экрана.
3. Изменение состава прав существующей роли предупреждает о числе затронутых сотрудников до сохранения.
4. Удаление роли, назначенной сотрудникам, требует явного подтверждения с указанием их числа.
5. Все действия скрыты/задизейблены без соответствующего права.
6. Состояния empty/loading/error обработаны.
7. Привилегированные права и роли помечены; недоступные пользователю права неактивны, недоступная роль открывается только на просмотр.
