# 1.9.3. Employees Access Page

## Спецификация страницы интерфейса

* **Название страницы:** Сотрудники
* **Модуль:** Управление клиникой (Clinic Management Module)
* **Владеющий бэкенд-модуль:** Auth Module (учётная запись), HR Module — только на чтение (ФИО, должность, отдел)
* **Тип страницы:** Реестр + карточка авторизационных данных
* **Основные роли:** Администратор клиники (`AUTH_USER_*`)
* **Маршрут:** `/clinic-management/employees`
* **Статус документа:** Актуализировано

> Общие паттерны — см. `1.9.0. Clinic Management Overview`. Бэкенд-контракт — `AuthModule.md` §6.1 (Users API), §6.3 (User-Roles), §6.4 (User-Permissions), §6.5 (`change-password`).

---

## Назначение страницы и сценарии использования

**Эта страница не создаёт, не редактирует и не удаляет сотрудников** — приём, увольнение, перевод, кадровые данные (ФИО, документы) полностью принадлежат HR Module (`1.6`) и здесь недоступны ни в каком виде. Учётная запись (`users`) создаётся автоматически при приёме сотрудника в HR Module (`AuthApplicationService.createUser`, `AuthModule.md` §6.1) — страница появляется в списке только для уже существующих учётных записей.

Назначение страницы — управление **исключительно авторизационным слоем** существующей учётной записи:

1. Просматривать список сотрудников с их ролями (ФИО и должность — только для отображения, подтягиваются из HR Module).
2. Назначать/снимать роли сотруднику.
3. Назначать/снимать точечные (персональные) права сотруднику в обход ролей.
4. Сбрасывать пароль.
5. Принудительно завершать все сеансы сотрудника (вывести из системы на всех устройствах).

## User Flows / Task Flows

### Flow 1. Просмотр и поиск

1. Таблица: ФИО (из HR), логин, роли (чипы).
2. Поиск по ФИО/логину, фильтр по роли.
3. Клик по строке → карточка сотрудника.

### Flow 2. Назначение/снятие ролей

1. В карточке — блок «Роли»: текущие роли чипами, «+ Добавить роль» открывает select с поиском по списку ролей (`1.9.2`).
2. Назначение → `POST /api/v1/user-roles/assign` (`{ roleIds: [id], userIds: [id] }`).
3. Снятие роли (крестик на чипе) → `POST /api/v1/user-roles/revoke`.
4. Попытка снять последнюю роль без замены — предупреждение «Без роли сотрудник теряет доступ к системе» с явным подтверждением (создание пользователя без роли невозможно на этапе HR-приёма, но снятие всех ролей постфактум технически не заблокировано бэкендом — UI обязан предупредить).

### Flow 3. Точечные права

1. Блок «Дополнительные права» — отдельно от ролей: список персональных прав сотрудника (`users.permissions`) с той же матрицей-компонентом, что и в `1.9.2`, но без сохранения как именованной роли.
2. Назначение/снятие → `POST /api/v1/user-permissions/assign` / `.../revoke` (`{ permissions: number[], userIds: [id] }`).
3. Блок используется точечно (эскалация/ограничение конкретного сотрудника без создания под него отдельной роли) — интерфейс явно подписывает его как исключение из общего правила «права через роль», чтобы администратор не путал точечные права с ролью.

### Flow 4. Сброс пароля

Администратор устанавливает новый пароль **без знания старого** — отдельный административный эндпоинт (`POST /api/v1/users/{id}/reset-password`, `AuthModule.md` §6.1a), не `change-password` (тот требует знания старого пароля и предназначен для самого пользователя).

1. «Сбросить пароль» → модаль с выбором: «Сгенерировать автоматически» (по умолчанию) или «Задать пароль вручную» (поле ввода, та же политика паролей, что при создании сотрудника).
2. Подтверждение → `POST /api/v1/users/{id}/reset-password`. **Пароль администратору не показывается** — в отличие от создания сотрудника в HR (где пароль возвращается в ответе API и показывается один раз): при административном сбросе новый пароль доставляется сотруднику напрямую через Notifications Module, по умолчанию SMS-сообщением на номер, привязанный к сотруднику (`NotificationsModule.md` §5.2, §15). Это осознанное отличие от Flow создания сотрудника — администратору не обязательно знать пароль, который он сам не будет сообщать.
3. Результат — toast, не модаль с паролем: «Новый пароль отправлен сотруднику по SMS» (обычный случай) либо, если у сотрудника нет способа связи для уведомления (редкий случай — контакт не заведён/устройство не привязано), предупреждение «Не удалось отправить пароль сотруднику — повторите сброс, задав пароль вручную» — при этом типе ошибки повторный сброс в режиме «вручную» обязателен, иначе введённый сервером пароль не узнает никто.

### Flow 5. Принудительный выход из системы

1. В карточке сотрудника — кнопка **«Завершить все сеансы»** (второстепенная, «опасного» цвета, рядом со сбросом пароля).
2. Нажатие открывает диалог подтверждения: «Сотрудник будет немедленно выведен из системы на всех устройствах и вернётся на страницу входа. Занятые им окна электронной очереди будут освобождены. Несохранённые данные сотрудника могут быть потеряны.» Кнопки: «Отмена» и «Завершить сеансы».
3. После подтверждения — сообщение «Сеансы сотрудника завершены». Если у сотрудника не было активных сеансов, действие всё равно считается выполненным.
4. Учётная запись при этом не блокируется: сотрудник может сразу войти снова под своим паролем. Чтобы лишить доступа, снимаются роли и права (Flow 2, 3); чтобы сменить доступ немедленно — сначала снимаются роли/права, затем завершаются сеансы.
5. Обычный самостоятельный выход и блокировка экрана по бездействию окно электронной очереди не освобождают; принудительный выход — освобождает.

## Визуал: High-Fidelity mockups

1. Блок ФИО/должности в карточке визуально помечен как read-only (приглушённый цвет, без кнопки редактирования) с подписью-ссылкой «Изменить в HR» — ведёт на карточку сотрудника в `1.6`, не дублирует форму.
2. Блок «Дополнительные права» визуально отделён от «Ролей» (другой фон/рамка) — это разные механизмы, смешение недопустимо.
3. Показ сгенерированного пароля (Flow 4) — модаль с моноширинным шрифтом значения и кнопкой копирования, тем же паттерном, что при создании сотрудника в HR.

## Состояния и edge cases

| Состояние | Ожидаемое поведение |
|---|---|
| loading | Skeleton списка/карточки |
| empty | Сотрудников нет — нейтральный текст (сотрудник появляется здесь только после приёма в HR, страница не предлагает создание) |
| error | Toast при сбое операций с ролями/правами/паролем |
| permissions | `AUTH_USER_READ` — просмотр; операции ниже — по своим правам |

### Edge cases

1. Снятие роли, требующей 2FA-подобных или иных специальных условий доступа, не предусмотрено бэкендом в этой версии — открытый вопрос снят вместе с исключением страницы «Подключение 2FA» из текущего состава модуля.
2. Сброс пароля завершает все сессии сотрудника: он выходит из системы на всех устройствах и входит заново с новым паролем, который приходит ему по SMS. Лишить доступа без смены пароля можно снятием ролей и прав (Flow 2, 3) — новые права действуют сразу, при ближайшем действии сотрудника, без перелогина; отдельное действие «Завершить все сеансы» (Flow 5) завершает сессии без смены пароля; при увольнении сессии завершаются автоматически. Блокировки учётной записи в системе нет.
3. Сотрудник без назначенной роли (после ручного снятия всех ролей, Flow 2) — сохраняет учётную запись, но не может авторизоваться содержательно (пустой набор прав); строка в списке помечается предупреждающим бейджем «Без роли».

## Interaction & Animation

1. Открытие карточки — slide-in справа, идентично паттерну карточек в HR/Warehouse.
2. Добавление/снятие роли или права — чип появляется/исчезает с fade, без перерисовки всей карточки.
3. Модаль показа пароля — fade+scale, копирование по клику с коротким «Скопировано» тултипом.

## Acceptance criteria

1. Страница не содержит ни одного элемента создания/редактирования/удаления кадровых данных — только переход в HR для этого.
2. Роли и точечные права редактируются раздельными блоками с разными эндпоинтами.
3. Сброс пароля показывает новый пароль один раз в защищённой модали.
4. Снятие последней роли сотрудника явно предупреждает о потере доступа.
5. Все операции скрыты/задизейблены без соответствующего права.
6. Состояния empty/loading/error обработаны.
