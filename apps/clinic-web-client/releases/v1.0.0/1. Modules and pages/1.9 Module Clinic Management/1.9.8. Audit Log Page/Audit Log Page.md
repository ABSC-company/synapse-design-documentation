# 1.9.8. Audit Log Page

## Спецификация страницы интерфейса

* **Название страницы:** История аудита
* **Модуль:** Управление клиникой (Clinic Management)
* **Позиция в модуле:** Восьмая страница (после `1.9.7. Reception and Queues Page`)
* **Тип страницы:** Реестр (read-only, без единого мутирующего действия)
* **Основные роли:** Администратор (по умолчанию — единственная роль с доступом, право не выдаётся рядовым сотрудникам)
* **Маршрут:** `/clinic-management/audit-log`
* **Платформа:** веб-приложение медицинской системы
* **Статус документа:** Draft (документ восстанавливает пропуск — страница уже задокументирована во frontend-пакете, `1.9.8. Audit Log — Frontend Spec`, но не имела отдельного дизайн-документа)
* **Связанная бэкенд-документация:** `AuditModule.md` §5 (схема `audit_logs`), §7 (REST API), §8 (права)

> Общие паттерны модуля (статус-бейджи, подтверждающие диалоги, права) — см. `1.9.0. Clinic Management Overview`. Страница целиком read-only — раздел «Подтверждающие диалоги на необратимые действия» из Overview к ней не применяется (мутирующих действий нет).

## Назначение страницы и сценарии использования

Реестр истории всех бизнес-изменений в системе по API-запросам сотрудников (`AuditModule.md` §1), а также вход/выход сотрудников из системы, включая неуспешные попытки входа. Страница ничего не создаёт, не редактирует и не удаляет — у Audit Module нет ни одного мутирующего эндпоинта для клиента (`AuditModule.md` §8); единственное действие пользователя — просмотр и фильтрация.

Ключевые задачи страницы:

1. Просмотр хронологического реестра событий аудита с фильтрами и полнотекстовым поиском.
2. Просмотр детальной карточки события: кто, что, когда, из какого модуля, с diff «до/после», если он был передан модулем-источником.
3. Расследование инцидентов безопасности — неуспешные попытки входа, действия конкретного сотрудника за период.

## User Flows / Task Flows для страницы

### Flow 1. Просмотр и фильтрация реестра

1. Администратор открывает «Историю аудита» — по умолчанию список отсортирован по дате, новые сверху, без предустановленных фильтров.
2. Открывает панель фильтров: сотрудник (асинхронный поиск по ФИО), модуль (мультивыбор чекбоксами), действие (зависимый список от выбранного модуля), тип сущности (аналогично), период дат.
3. Применяет фильтры — таблица обновляется, активные фильтры отображаются чипами под шапкой с возможностью снять каждый по отдельности.
4. Дополнительно — свободный полнотекстовый поиск в шапке страницы (по описанию/модулю/сущности), независимый от панели фильтров.

### Flow 2. Просмотр детали события

1. Клик по строке реестра открывает модальное окно с полной карточкой события.
2. Верх карточки — человекочитаемое описание («Иванов И.И. назначил Петрову А.С. на должность «Хирург»»), если модуль его передал; иначе — технический вид `METHOD /route`.
3. Ниже — атрибуты события (сотрудник, модуль, действие, сущность, дата/время, статус ответа, маршрут, IP).
4. Если модуль передал снимки «до/после» — блок «Изменения» с построчным diff по ключам; если снимков нет — блок не отображается вовсе.
5. Если у сущности события есть соответствующая карточка на фронте (например, сотрудник, документ) — переход по клику; если нет — обычный текст.

### Flow 3. Расследование неуспешных попыток входа

1. Администратор фильтрует по модулю «Авторизация» и действию «Неудачная попытка входа».
2. В реестре видны все попытки за период, включая случаи с несуществующим логином (сотрудник в строке — «—», сохранён только сам введённый логин, доступный в детальной карточке).
3. Статус-бейдж ответа (`4xx`) визуально выделяет неуспешные попытки в общем потоке событий.

### Flow 4. Хронология действий конкретного сотрудника

1. Администратор открывает выборку двумя способами: фильтр «Сотрудник» в панели фильтров либо кнопка «История действий» на карточке сотрудника (переход с уже применённым фильтром).
2. Над таблицей появляется чип «Сотрудник: ФИО» и чип периода (по умолчанию — последние 30 дней), оба снимаются по отдельности.
3. В реестре — все действия этого сотрудника, включая вход/выход и неудачные попытки входа под его учётной записью. Порядок — новые сверху; клик по заголовку «Дата/время» переключает на «от старых к новым» для последовательного чтения событий.
4. Фильтр по сотруднику комбинируется с модулем, действием, периодом и полнотекстовым поиском.
5. Действия, совершённые над сотрудником другими людьми, в эту выборку не входят — они ищутся по сущности «Сотрудник».

Общий layout страницы:

1. Слева: Sidebar в свёрнутом состоянии.
2. Сверху: **Page Header** — «История аудита» + поле полнотекстового поиска + кнопка «Фильтры» (со счётчиком активных).
3. Контентная область: чипы активных фильтров (если есть) → таблица реестра → пагинация.
4. Панель фильтров — выезжающий drawer справа. Деталь события — модальное окно поверх реестра.

## Структура: Wireframes

### Таблица реестра

| Колонка | Описание |
|---|---|
| Дата/время | Момент завершения запроса, сортировка по умолчанию — новые сверху; заголовок кликабелен — переключение «новые сверху» ⇄ «старые сверху» со стрелкой-индикатором направления |
| Сотрудник | ФИО, кликабельно (переход на карточку сотрудника при наличии права) либо «—» для неаутентифицированных попыток входа |
| Модуль | Бейдж с человекочитаемым названием (HR, Склад, Документооборот, Авторизация и т.д.) |
| Действие | Человекочитаемый текст, если событие обогащено; иначе приглушённый моноширинный `METHOD /route` |
| Сущность | Тип + идентификатор либо «—» |
| Статус | Бейдж кода ответа: `2xx` — нейтральный/зелёный, `4xx`/`5xx` — жёлтый/красный |

Каждая строка кликабельна — no-op строк в реестре нет.

## Визуал: High-Fidelity mockups

Визуальные правила:

1. Бейдж модуля — единая цветовая карта кодов модулей, переиспользующая маппинг названий из навигации (`1.9.0. Overview`), а не произвольные цвета per-страница.
2. Необогащённые записи (`description = null`) визуально приглушены (моноширинный шрифт, вторичный цвет текста) — сразу отличимы от обычных человекочитаемых строк, без отдельной легенды.
3. Статус-бейдж ответа — та же цветовая семантика, что и везде в модуле (зелёный/жёлтый/красный, `1.9.0. Overview`), не отдельная палитра для этой страницы.
4. Diff «до/после» в карточке — плоский список ключ → значение в две колонки, без попытки визуально резолвить значения (id остаются как есть) — техническая деталь для администратора, не пользовательская форма.
5. Чипы активных фильтров — компактные, с крестиком снятия на каждом, отдельно от кнопки «Сбросить» в drawer.

Визуальные компоненты, обязательные к отрисовке в mockups:

1. Таблица реестра с разными статусами ответа и обогащёнными/необогащёнными записями вперемешку.
2. Панель фильтров (drawer) со всеми полями, включая зависимое «Действие».
3. Карточка события с блоком diff и без него (два состояния).
4. Чипы активных фильтров под шапкой.
5. Состояния loading/empty/error.

## Состояния и edge cases

| Состояние | Ожидаемое поведение |
|---|---|
| loading | Skeleton таблицы при первой загрузке/смене фильтра |
| empty (по фильтру) | «Ничего не найдено» + кнопка «Сбросить фильтры» |
| empty (данных вообще нет) | «История аудита пуста» — отдельная формулировка от «ничего не найдено по фильтру» |
| error | Сообщение + «Повторить», как на остальных реестровых страницах модуля |
| offline | Реестр — из последнего кэша с пометкой неактуальности; открытие карточки нового события недоступно |
| permissions | Страница и пункт меню полностью скрыты без `AUDIT_LOG_GET` — не отображаются как disabled |

### Edge cases

1. Неуспешная попытка входа с несуществующим логином — `Сотрудник = "—"`, сам введённый логин виден только в детальной карточке (не в списке, чтобы не загромождать реестр потенциально «мусорными» значениями).
2. Событие без обогащения (`description = null`) — заголовок карточки тоже технический (`METHOD /route`), а не пустая строка.
3. Событие без `entity_type`/`entity_id` (например, вход/выход) — колонка «Сущность» показывает «—», это штатное состояние, не ошибка данных.
4. Очень большой объём результатов по широкому фильтру (например, весь модуль HR за год) — обычная пагинация реестра, без ограничения периода на уровне UI (ограничение производительности — зона ответственности бэкенда, `AuditModule.md` §9).
5. Полнотекстовый поиск — не поиск «на лету» по каждому символу (debounce 300–400 мс), в отличие от `ILIKE`-поиска других реестров модуля — визуально это не должно выглядеть как «зависание», используется тот же индикатор загрузки, что у остальных фильтров.

## Interaction & Animation

1. Открытие панели фильтров — slide-in справа, 300ms, как в `1.5.1. Documents Page`.
2. Открытие карточки события — модаль с fade+scale.
3. Применение фильтра — таблица обновляется с коротким skeleton, без полной перезагрузки страницы.
4. Снятие фильтра-чипа — мгновенное, без подтверждения (действие полностью обратимо повторным выбором).
5. Зависимые поля («Действие», «Тип сущности») — при смене «Модуль» плавно сбрасываются и переходят в состояние «недоступно» до нового выбора.

## Зависимости и ограничения

### API

1. `GET /audit/logs` — список с фильтрами, поиском и пагинацией (`AuditModule.md` §7).
2. `GET /audit/logs/:id` — детальная карточка события, включая `before`/`after`, `ip`, `user_agent` (§7).
3. `GET /audit/logs/modules`, `GET /audit/logs/actions?module=`, `GET /audit/logs/entity-types?module=` — справочники для панели фильтров (§7.1) — не хардкод на фронте, новый доменный модуль появляется в фильтрах автоматически.

### Роли и права

1. `AUDIT_LOG_GET` (15000) — единственное право страницы: просмотр реестра и карточек событий. Модуль не имеет ни одного мутирующего эндпоинта для клиента, отдельного права на «управление» не существует.

## Acceptance criteria

1. Реестр отображает события аудита в хронологическом порядке (новые сверху) с фильтрами по сотруднику, модулю, действию, типу сущности и периоду.
2. Свободный полнотекстовый поиск в шапке работает независимо от панели фильтров.
3. Клик по строке открывает карточку события с полным описанием, атрибутами и (если переданы) diff «до/после».
4. Необогащённые записи (`description = null`) визуально отличимы от обогащённых во всех местах отображения (реестр и карточка).
5. Списки опций фильтров «Модуль»/«Действие»/«Тип сущности» подтягиваются с бэкенда, а не захардкожены на фронте.
6. Все состояния (loading/empty×2/error/offline/permissions) реализованы согласно таблице выше.
7. Страница и пункт меню полностью недоступны без права `AUDIT_LOG_GET`.
8. Фильтр по сотруднику показывает все действия сотрудника (включая вход/выход и неудачные попытки входа) в корректной хронологии, с переключением направления сортировки; комбинируется с остальными фильтрами и поиском.
9. С карточки сотрудника доступен переход в реестр аудита с предустановленным фильтром по этому сотруднику (при наличии `AUDIT_LOG_GET`).
