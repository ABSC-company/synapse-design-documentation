# 1.9.1. Global Settings Page

## Спецификация страницы интерфейса

* **Название страницы:** Глобальные настройки
* **Модуль:** Управление клиникой (Clinic Management Module)
* **Владеющий бэкенд-модуль:** Management Module
* **Тип страницы:** Динамическая форма по разделам (chapters)
* **Основные роли:** Администратор клиники (`MGMT_SETTINGS_MANAGE`)
* **Маршрут:** `/clinic-management/settings`
* **Статус документа:** Актуализировано

> Общие паттерны — см. `1.9.0. Clinic Management Overview`. Бэкенд-контракт — `ManagementModule.md` §3 (формат схем настроек), §5.9–§5.10 (получение/обновление), §6 (системные стандарты).

---

## Назначение страницы и сценарии использования

Страница — единственная точка редактирования глобальных настроек клиники после завершения мастера первичной настройки (`1.1. Initialization`, этап 3). Она **не содержит собственной бизнес-логики настроек**: список разделов и схема каждого раздела приходят с сервера как есть (`ManagementModule.md` §3.2) и отрисовываются универсальным рендерером формы — добавление новой настройки на бэкенде не требует изменений фронтенда этой страницы.

С помощью страницы пользователь может:

1. Просматривать список разделов настроек (`chapters`), сгруппированных по владеющему модулю.
2. Открывать раздел и редактировать значения его настроек в соответствии с типом каждого поля (`input`, `select`, `checkbox`, `file-input`, `remote-select`, `collection` и т.д. — `ManagementModule.md` §3.2).
3. Сохранять раздел целиком (частичное сохранение отдельных полей не предусмотрено бэкендом).
4. Выбирать активный вариант системного стандарта (пол, группы крови, классификаторы МКБ и т.д.) там, где настройка — это выбор одного из готовых вариантов (`ManagementModule.md` §6).
5. Загружать/заменять логотип клиники.

## User Flows / Task Flows

### Flow 1. Просмотр списка разделов

1. Страница запрашивает `GET /management/settings/chapters` — получает список `{ name, file_name }`.
2. Разделы отображаются как список карточек/строк в левом сайдбаре страницы (навигация «раздел → форма» внутри одной страницы, без перехода по отдельным маршрутам).

### Flow 2. Редактирование раздела

1. Пользователь выбирает раздел — фронт запрашивает `GET /management/settings/chapters/{fileName}`, получает полную схему раздела «как есть».
2. Форма отрисовывается рекурсивно по `settings[].schema[]`: каждый узел — компонент по своему `type` (см. таблицу ниже).
3. Пользователь редактирует значения; кнопка «Сохранить» становится активной при первом изменении.
4. По «Сохранить» фронт отправляет **всю схему раздела** (с изменёнными `value`) через `PUT /management/settings/chapters/{fileName}` — сервер сам выполняет дегидратацию и валидацию (`ManagementModule.md` §3.5).
5. Ошибка `400 INVALID_SETTING_VALUE` — инлайн-подсветка конкретного поля по пути, вернувшемуся в `details` ответа, без сброса остальной формы.

### Flow 3. Настройка типа `remote-select`

1. Поле ссылается на сущность другого модуля (например, отдел из Structure Module) — фронт самостоятельно запрашивает список по `remote.endpoint`, отображает `remote.key`, сохраняет `remote.value` (`ManagementModule.md` §3.2.1).
2. Такие поля доступны только после инициализации системы — на этой странице ограничение уже неактуально (страница открывается только при `initialized: true`), поэтому дополнительно не обрабатывается.

### Flow 4. Выбор системного стандарта

1. Настройка типа `select`, чьи `acceptable_values` соответствуют вариантам стандарта (например, `hr.gender.active_variant_id`), отображается как обычный select — семантика «это стандарт» видна пользователю только по описанию (`description`) настройки, отдельного UI-паттерна не требуется.
2. Смена значения = обычное сохранение раздела (Flow 2); сервер проверяет, что id варианта существует в файле стандарта, иначе `404 VARIANT_NOT_FOUND`.

### Flow 5. Загрузка логотипа клиники

1. Поле `general.logo_id` (`file-input`) — клик открывает системный выбор файла.
2. Фронт сразу вызывает `PUT /management/clinic/logo` (отдельный эндпоинт, не через дегидратацию раздела) — получает `logo_id`, подставляет его в значение поля формы.
3. Итоговое сохранение раздела `general` (Flow 2) фиксирует уже готовый `logo_id`.

### Компоненты по типу поля (`ManagementModule.md` §3.2)

| `type` | UI-компонент |
|---|---|
| `input` | текстовое поле |
| `number-input` | числовое поле |
| `select` | выпадающий список, один выбор |
| `select-multi` | выпадающий список, множественный выбор (чипы) |
| `checkbox` | переключатель |
| `file-input` | загрузчик файла с превью |
| `remote-select` | выпадающий список с асинхронной подгрузкой (Flow 3), с индикатором загрузки |
| `collection` | повторяющийся блок-группа — «+ Добавить» добавляет новую строку с тем же набором вложенных полей |

## Визуал: High-Fidelity mockups

1. Двухколоночный layout: список разделов слева (sticky), форма справа — идентично шаблону настроек в остальных крупных модулях.
2. Кнопка «Сохранить» раздела — sticky в шапке правой колонки, задизейблена, пока нет несохранённых изменений.
3. `collection`-блоки визуально обособлены рамкой/карточкой на всю ширину формы, с кнопкой удаления строки и «+ Добавить» под последней строкой.
4. Индикатор несохранённых изменений — точка/бейдж рядом с названием раздела в левом списке.

## Состояния и edge cases

| Состояние | Ожидаемое поведение |
|---|---|
| loading | Skeleton формы при открытии раздела |
| empty | Список разделов пуст — не ожидается в норме (`chapters.json` всегда непустой), но обрабатывается нейтральным текстом |
| error | Ошибка загрузки схемы раздела — блок ошибки + «Повторить»; ошибка сохранения — toast с текстом из `ErrorResponse.message`, форма не сбрасывается |
| permissions | Вся страница недоступна без `MGMT_SETTINGS_MANAGE` (Overview больше не применим — до этой ревизии страница была доступна и до инициализации, но модуль управления клиникой целиком открывается только после неё) |

### Edge cases

1. Уход со страницы/переключение раздела с несохранёнными изменениями — подтверждающий диалог «Изменения не сохранены».
2. `collection` с вложенным `collection` (двойная вложенность) — рендерится рекурсивно тем же компонентом, без ограничения по глубине на UI (ограничение, если появится, — со стороны бэкенд-схемы).
3. Поле `remote-select`, чей `remote.endpoint` вернул ошибку, — поле показывает состояние ошибки загрузки списка с кнопкой «Повторить» локально для этого поля, не блокируя остальную форму.
4. Параллельное редактирование раздела двумя администраторами — оптимистичная блокировка не предусмотрена бэкендом; последняя сохранённая версия побеждает (открытый вопрос для будущей ревизии — конфликты не разрешаются на UI).

## Interaction & Animation

1. Переключение раздела — контент справа плавно fade, список слева не перерисовывается.
2. Сохранение — кнопка переходит в состояние загрузки (спиннер), после успеха — короткий success-flash.
3. `collection` — добавление строки со slide-down анимацией, удаление — slide-up с fade.

## Зависимости и ограничения

### API

1. `GET /management/settings/chapters` — список разделов.
2. `GET /management/settings/chapters/{fileName}` — схема раздела.
3. `PUT /management/settings/chapters/{fileName}` — сохранение раздела (без `?finalize` — этот параметр используется только мастером инициализации).
4. `PUT /management/clinic/logo` — загрузка логотипа (Flow 5).

### Роли и права

| Действие | Право |
|---|---|
| Просмотр и редактирование любого раздела | `MGMT_SETTINGS_MANAGE` |

Права настройки не различаются по разделам — управление глобальными настройками не делится на более мелкие права (см. `ManagementModule.md` §7).

---

## Acceptance criteria

1. Список разделов и форма каждого раздела строятся полностью по схеме с сервера, без хардкода конкретных настроек на фронте.
2. Каждый `type` поля из §3.2 бэкенд-документации имеет соответствующий UI-компонент.
3. Сохранение раздела отправляет полную схему с изменёнными `value` и обрабатывает `400 INVALID_SETTING_VALUE` инлайн-ошибкой на конкретном поле.
4. Логотип клиники загружается отдельным вызовом до сохранения раздела `general`.
5. Страница целиком недоступна без `MGMT_SETTINGS_MANAGE`.
6. Уход со страницы с несохранёнными изменениями подтверждается диалогом.
