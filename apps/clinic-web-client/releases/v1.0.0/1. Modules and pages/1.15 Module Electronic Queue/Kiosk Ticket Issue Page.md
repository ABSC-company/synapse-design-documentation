# Kiosk — терминал выдачи талонов

## Спецификация страницы интерфейса

* **Название:** Киоск выдачи талонов
* **Модуль:** Электронная очередь (Electronic Queue Module)
* **Тип:** публичный терминал, без пользователя-сотрудника
* **Маршрут:** `/electronic-queue/kiosk`
* **Статус документа:** Актуализировано (**рабочий режим расписан как три экрана — выбор языка, выбор точки очереди, получение номера; явно учтено, что один киоск обслуживает несколько точек очереди**; ранее добавлена привязка устройства одноразовым кодом — устройство больше не выдаёт талоны анонимно; настройка обслуживаемых точек очереди перенесена с самого устройства на `1.9.7. Reception and Queues Page`; токен привязки теперь передаётся `httpOnly`-cookie, а не хранится в `localStorage` — киоск-страница никогда не видит сам токен)

> Второй документ модуля — `Queue Display Monitors.md` (мониторы, на которых отображается результат работы этого киоска). Бэкенд-контракт — `ElectronicQueueModule.md` §4.3 (талон), §4.4 (сущность киоска), §6.1 (сценарий выдачи и вызова), §6.10 (привязка одноразовым кодом), §8, §12.4 (`POST /queue-points/:id/tickets/kiosk`), §12.6 (Kiosks API). Создание записи киоска и получение кода привязки — на `1.9.7. Reception and Queues Page`, раздел «Киоски» (Flow 7, Flow 9) — этот документ описывает только экран самого физического устройства.

---

## Назначение

Экран расположен в зоне ожидания, рассчитан на самостоятельное использование пациентом без помощи персонала. Единственная задача — выдать номер-бюллетень (талон), с которым пациент встаёт в электронную очередь выбранной им точки (регистратуры, приёма врача и т.п.).

**Один киоск может обслуживать несколько точек очереди.** Список точек — не локальная настройка устройства, а то, что администратор задал записи киоска на `1.9.7` (`queue_kiosk_points`, `ElectronicQueueModule.md` §4.4). Типичные случаи: киоск в общем холле, с которого выдают талоны в регистратуру, к терапевту и на сдачу анализов; либо киоск, привязанный к единственной точке. Поэтому пациент проходит по киоску **три экрана подряд**: выбор языка → выбор точки очереди → получение номера (см. «Сценарий пациента»). Выбор точки — это выбор пациента из списка, разрешённого администратором; устройство никогда не предлагает точку, которой нет в этом списке.

## Привязка устройства (первый запуск / после сброса)

**Путь устройства от коробки до работы:** (1) администратор на `1.9.7` создаёт запись киоска, задаёт **список точек очереди** и получает **одноразовый 4-значный код** (Flow 7; статус «Ожидает привязки»); (2) на физическом киоске открывается `/electronic-queue/kiosk` → экран ввода кода; (3) верный код → статус «Подключено», киоск показывает экран 1 «Выбор языка»; (4) список точек правится на `1.9.7` без повторной привязки, замена устройства/отзыв доступа — перевыпуск кода (Flow 9).

Отдельный экран **до** обычной работы киоска. В отличие от предыдущей ревизии, страница не хранит токен сама и не может по своему усмотрению определить «я уже привязан» без обращения к серверу — токен передаётся `httpOnly`-cookie (`eq_kiosk_token`), недоступной для чтения из JS (`AuthModule.md` §15.1, §15.4, `ElectronicQueueModule.md` §6.10): при каждом открытии страница сразу пробует загрузить рабочий экран (`GET /kiosks/me`, см. «Технические детали»), и только получив `401 Unauthorized`, показывает экран ввода кода.

**Экран ввода кода.** Один крупный элемент по центру: поле ввода 4-значного кода (буквы и цифры, регистр важен — код вводится ровно так, как показан администратору) + кнопка «Подтвердить». Заголовок поясняет: «Введите код, полученный от администратора клиники». Без ссылки «забыли код» — код выдаётся и при необходимости перевыпускается только на `1.9.7`, экран устройства не может его показать или напомнить.

- Верный код → `POST /api/v1/electronic-queue/kiosks/pair` погашает код и **выставляет браузеру `httpOnly`-cookie** с сервисным токеном киоска (`ElectronicQueueModule.md` §6.10, §12.6) — страница никогда не получает и не хранит сам токен, только список разрешённых точек очереди из тела ответа, и сразу переходит к обычной работе — экрану 1 «Выбор языка» (см. «Сценарий пациента»), без промежуточного «Готово».
- Неверный код (`401 INVALID_PAIRING_CODE`) → инлайн-ошибка «Код неверный», попытку можно повторить сразу; после нескольких быстрых неудачных попыток подряд — короткая задержка перед следующей попыткой (клиентская защита поверх серверного rate limiting, `ElectronicQueueModule.md` §10).
- Истёкший код (`401 PAIRING_CODE_EXPIRED`) → отдельная инлайн-подсказка «Код истёк — обратитесь к администратору клиники за новым кодом», без права угадать по-другому: киоск не умеет запросить новый код сам.
- Устройство, у которого администратор отозвал доступ перевыпуском кода (`ElectronicQueueModule.md` §6.10), — при следующем обращении к серверу (печать талона либо проверочный `GET /kiosks/me`) получает `401 Unauthorized`; страница реагирует так же, как на первый запуск — показывает экран ввода кода заново (очищать локально нечего — токена на странице никогда и не было).

## Сценарий пациента: три экрана

Рабочий режим киоска (после привязки) — всегда одна и та же последовательность. Пациент двигается только вперёд; на экранах 2 и 3 есть кнопка «Назад»/«В начало», на экране 1 — нет.

```
 Экран 1              Экран 2                     Экран 3
 Выбор языка   ──►    Выбор точки очереди   ──►   Ваш номер
 [ Ўзбекча ]          [ Регистратура ]            A-014
 [ Русский ]          [ Терапевт     ]            Подойдите к окну… / Следите за табло
 [ English ]          [ Анализы      ]            (автовозврат на экран 1)
```

**Экран 1 — выбор языка.** Крупные кнопки по одной на язык интерфейса, на самом языке («Ўзбекча», «Русский», «English» — состав и порядок задаются настройкой клиники, не пациентом). Это экран покоя киоска: именно он виден, пока устройство ждёт пациента. Выбор языка применяется ко всем следующим экранам и к тексту чека; сам по себе он ничего не печатает — случайное касание не создаёт талон. Выбранный язык нигде не сохраняется после завершения сессии пациента (см. «Возврат на экран 1»).

**Экран 2 — выбор точки очереди.** Показывает кнопки точек из `KioskMeDto.queue_points` (только активные, см. «Технические детали», п.4). Каждая кнопка — название точки очереди («Регистратура», «Терапевт», «Сдача анализов»), крупно, по одной в строку; список прокручивается только если точек не помещается на экране — для одного киоска это сигнал администратору сократить список, но экран не должен ломаться и при 6–8 точках. Нажатие на кнопку — **единственное действие, которое выдаёт талон** (запускает печать и переход на экран 3).
- **Одна точка у киоска.** Экран 2 не пропускается — он остаётся шагом подтверждения: одна крупная кнопка с названием точки и подписью «Получить номер». Так последовательность для пациента всегда одинакова, а случайное касание на экране выбора языка не печатает талон.
- **Ни одной активной точки** (список пуст либо все точки выключены администратором) — вместо кнопок сообщение «Выдача номеров временно недоступна, обратитесь в регистратуру» (то же поведение, что «Чек не печатается»; бэкенд при этом ответил бы `422 KIOSK_NO_QUEUE_POINTS`, пациент до такого запроса не доходит).

**Экран 3 — получение номера.** Сразу после нажатия — короткая пауза с индикатором, пока печатается чек (повторные нажатия в это время игнорируются). Затем крупно показывается напечатанный номер («Ваш номер: A-014») и точка, в которую он выдан («Регистратура»), — чтобы пациент мог свериться с чеком и понимал, к какому табло прислушиваться. Номер держится на экране несколько секунд (достаточно, чтобы прочитать), затем экран сам возвращается на экран 1. Кнопка «Готово» позволяет вернуться сразу — следующему пациенту не нужно ждать таймера.

**Возврат на экран 1.** Любая сессия пациента заканчивается возвратом на экран выбора языка и сбросом всего выбранного (язык, точка): после показа номера на экране 3 — по таймеру или «Готово»; на экранах 2 и 3 при бездействии (около 30–60 секунд без касаний) — автоматически, чтобы следующий пациент не увидел чужой выбор. Кнопка «Назад» с экрана 2 ведёт на экран 1.

## Состояния экрана

Ниже — состояния, общие для всей последовательности; состояние «по умолчанию» — это экран 1.

**После нажатия на точку**
Короткая пауза с индикатором прогресса, пока печатается чек, — чтобы пациент понимал, что нужно подождать, а не нажимать кнопку повторно.

**Талон выдан**
Экран 3 (см. выше).

**Чек не печатается**
Сообщение об ошибке и предложение обратиться к регистратору напрямую — киоск не должен становиться тупиковым сценарием для пациента.

**Не осталось бумаги для чека**
Отдельное состояние отказа — та же логика, что и «чек не печатается»: явное сообщение и переадресация к регистратору, а не бесконечная попытка печати.

**Нет связи с сервером**
Экран-заглушка «Сервис временно недоступен» вместо кнопки выдачи — киоск не должен выдавать талон, который не сможет отобразиться в очереди регистратора.

На чеке: номер талона, **название точки очереди** (когда киоск обслуживает несколько точек, номер без точки бессмыслен — «A-014» может быть и в регистратуру, и к терапевту), дата и время выдачи. Текст чека — на языке, выбранном на экране 1.

## Технические детали (для фронтенд-реализации)

1. **Проверка при загрузке страницы.** `GET /api/v1/electronic-queue/kiosks/me` — авторизация cookie `eq_kiosk_token` (браузер отправляет её автоматически, если она есть, JS её не читает и не проверяет сам). `200` → показывается экран 1 «Выбор языка» (см. «Сценарий пациента»); ответ (`KioskMeDto`, `ElectronicQueueModule.md` §12.6) содержит список разрешённых точек очереди (`queue_points: [{ id, name }]`) — страница держит его в памяти и использует для кнопок экрана 2. Список перечитывается при каждом возврате на экран 1 (то есть перед каждым новым пациентом), поэтому правка набора точек администратором на `1.9.7` подхватывается без перезагрузки страницы. `401` → показывается экран ввода кода привязки.
2. **Привязка.** `POST /api/v1/electronic-queue/kiosks/pair` (`{ code }`, публичный, без аутентификации, `ElectronicQueueModule.md` §12.6) → при успехе `KioskPairResponseDto` (`{ kiosk: { id, name } }`, **без поля `token`**) + `Set-Cookie: eq_kiosk_token=...; HttpOnly; Secure; SameSite=Strict` на самом ответе — браузер сохраняет cookie автоматически, странице ничего не нужно делать самой. Разрешённые точки очереди для отрисовки кнопок страница берёт из последующего `GET /kiosks/me` (п.1) либо, если бэкенд включает их сразу в ответ `pair`, — из него.
3. Нажатие кнопки точки на экране 2 → `POST /api/v1/electronic-queue/queue-points/:id/tickets/kiosk` (авторизация той же cookie `eq_kiosk_token`, отправляется браузером автоматически — не заголовком `Authorization`, **не публичный маршрут, в отличие от предыдущей ревизии**, `ElectronicQueueModule.md` §12.4) → `201` с `QueueTicketResponseDto` (`status: "waiting"`, `source: "kiosk"`). Номер для печати — поле `number` ответа (например `A-014`); `:id` — `id` выбранной точки. Выбранный на экране 1 язык на сервер **не передаётся** — он влияет только на тексты экранов и чека на самой странице.
4. `422 QUEUE_POINT_INACTIVE` — точка очереди выключена администратором (`1.9.7`): киоск не должен показывать кнопку для этой точки на экране 2 вовсе, а не выдавать ошибку по клику. Если ответ всё же пришёл (точку выключили между загрузкой списка и нажатием) — экран возвращается на экран 2 с сообщением «Эта очередь сейчас недоступна, выберите другую» и обновлённым списком.
7. **Язык и названия точек.** Тексты интерфейса и чека переключаются на клиенте по выбранному языку. Название точки (`queue_points[].name`) приходит с сервера в единственном экземпляре — переводов у точки очереди в контракте нет (`ElectronicQueueModule.md` §4.1, §12.6). Если клинике нужны названия на нескольких языках, потребуется расширение контракта (локализованные названия точки) — вне рамок этой ревизии, открытый вопрос.
5. `401 Unauthorized` на любом вызове (cookie отсутствует, невалидна или отозвана администратором через перевыпуск кода/удаление киоска, `ElectronicQueueModule.md` §6.10) — устройство сбрасывает локальное состояние (список точек) и показывает экран ввода кода заново; отдельного «выхода» не требуется — устройство не хранит ничего секретного, которое нужно было бы явно стереть.
6. `403 QUEUE_POINT_NOT_ALLOWED_FOR_KIOSK` не должен возникать в норме (экран не показывает кнопки для точек вне списка, полученного на шаге 1) — если всё же приходит (например, список устарел из-за правки администратором в моменте), обрабатывается как обычный отказ печати (см. «Состояния экрана», «Чек не печатается»), с обновлением списка точек при следующей загрузке экрана.

## Interaction & Animation

Печать чека сопровождается индикатором прогресса (см. «После нажатия»); возврат в состояние по умолчанию после показа номера — плавный, без резкого переключения.

## Acceptance criteria

1. При первом запуске (или после сброса/отзыва доступа) экран показывает только поле ввода кода привязки; после успешной привязки устройство переходит к обычной работе без дополнительного подтверждения.
2. Неверный и истёкший код дают разные, понятные без обращения к технической поддержке сообщения.
3. После привязки киоск всегда проходит три экрана: выбор языка → выбор точки очереди → получение номера. Талон создаётся только нажатием на точку на экране 2; выбор языка ничего не печатает. При единственной разрешённой точке экран 2 остаётся как подтверждение с одной кнопкой.
4. Выданный номер и название точки показываются крупно и достаточно долго, чтобы пациент успел свериться с чеком; на чеке — номер, точка, дата/время на выбранном языке.
4a. После показа номера, а также при бездействии на экранах 2–3, киоск автоматически возвращается на экран выбора языка и сбрасывает выбор предыдущего пациента.
4b. Один киоск корректно обслуживает несколько точек очереди: на экране 2 только активные точки из списка администратора, талон выдаётся строго в выбранную точку.
5. Отказ печати (в т.ч. нет бумаги) и отсутствие связи — явные, не тупиковые для пациента состояния.
6. Киоск печатает только по точкам очереди, разрешённым ему администратором на `1.9.7`; сам список задаётся администратором, на устройстве пациент лишь выбирает из него точку (экран 2).
7. Отзыв доступа администратором (перевыпуск кода/удаление киоска) переводит устройство обратно к экрану ввода кода при следующем обращении к серверу, без ручного вмешательства на самом устройстве.
