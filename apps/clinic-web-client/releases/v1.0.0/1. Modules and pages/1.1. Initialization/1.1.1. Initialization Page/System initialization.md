# 1.1.1. System Initialization Page

## Спецификация страницы интерфейса

* Название страницы: Инициализация системы
* Модуль: Management
* Тип страницы: Первичная настройка клиники
* Основные роли: Администратор клиники, Оператор клиники
* Статус документа: Актуализировано по документации бэкенда (ManagementModule, все этапы)
* Платформа: веб-приложение для медицинской системы

---

# Назначение страницы и сценарии использования

Страница предназначена для первоначальной настройки системы после установки. С помощью страницы пользователь может:

1. Указать название клиники и загрузить логотип.
2. Создать первого администратора системы (роль, должность, учётная запись сотрудника).
3. Указать адрес клиники, региональные настройки, расписание работы и название первого отдела.
4. Настроить системные параметры (опционально — можно пропустить и настроить позже).
5. Завершить процесс активации системы.

После успешного завершения инициализации пользователь получает возможность авторизоваться и работать в системе.

**Важная особенность логики (соответствует бэкенду):** данные Шагов 1–3 (клиника, администратор, адрес и график) технически являются одним атомарным запросом на сервере. Именно поэтому в мастере они собираются локально и отправляются на сервер одним запросом только в момент завершения этих трёх шагов (при переходе к Шагу 5). До этого момента пользователь может свободно возвращаться назад и менять любые введённые данные — ничего не считается окончательным. Если при создании возникает ошибка — сервер откатывает всё созданное в рамках этого запроса (транзакция), система остаётся неинициализированной, и пользователь может повторить попытку.

Шаг 4 (настройки системы) — **отдельный, опциональный** этап. Без него система считается настроенной: пользователь либо пропускает этот этап целиком (настройки остаются значениями по умолчанию и меняются позже), либо проходит его — тогда изменённые параметры отправляются вместе с остальными данными в момент нажатия «Завершить настройку» на Шаге 5 (см. «Шаг 5. Завершение»).

Логотип клиники отправляется вместе с остальными данными Шагов 1–3 в том же запросе: до Шага 5 файл хранится только в мастере.

Основная рабочая область страницы. Отображает контент текущего шага. Контент может прокручиваться независимо от остальных элементов страницы.

## Footer

Закреплён в нижней части страницы. Содержит кнопки управления мастером:

* На первом шаге кнопка «Назад» скрыта.

* Переход между шагами 1–4 не приводит к обращению к серверу (кроме безусловного чтения списка/схем разделов настроек на Шаге 4 — см. далее) — реальное создание сущностей происходит только на Шаге 5.

# User Flows

## Flow 1. Полная настройка системы

1. Пользователь открывает страницу.
2. Указывает название клиники и (опционально) логотип.
3. Создаёт администратора (роль, должность, данные сотрудника).
4. Указывает адрес клиники, региональные настройки, график работы и первый отдел.
5. Настраивает параметры системы (или явно пропускает этот этап).
6. Завершает настройку — данные Шагов 1–3 отправляются одним запросом, вместе с ними отправляются изменённые настройки (если этап не пропущен).
7. Получает доступ к авторизации — только когда система полностью инициализирована.

---

## Flow 2. Клиника и логотип

1. Пользователь вводит название клиники.
2. Опционально выбирает изображение логотипа — файл проверяется (тип, размер) и показывается в предпросмотре.
3. Переходит к следующему шагу. Логотип необязателен, шаг проходится без него.

> **Изменение логики по сравнению с предыдущей версией документа:** сценарий с подключением клиники по конфигурационному JSON-файлу или QR-коду **удалён** — в логике инициализации нет ни такого механизма, ни отдельного шага подтверждения подлинности клиники. Клиника создаётся напрямую из введённых пользователем названия и логотипа.

---

## Flow 3. Создание администратора

1. Пользователь вводит название роли и название должности.
2. Вводит данные сотрудника-администратора (см. «Шаг 2. Администратор»).
3. Переходит к следующему этапу. Роль, должность и учётная запись фактически создаются только при завершении настройки на Шаге 5.

---

## Flow 4. Адрес и график работы

1. Пользователь указывает название первого отдела.
2. Настраивает местоположение (страна, город, адрес, координаты на карте).
3. Выбирает язык системы и часовой пояс, настраивает расписание работы.
4. Подтверждает данные и переходит дальше. Отдел и структура клиники фактически создаются только при завершении настройки на Шаге 5.

---

## Flow 5. Настройка системы (опционально)

1. Пользователь решает, настраивать ли систему сейчас, или пропустить этап и настроить его позже, после первого входа в систему (переключатель «Настроить сейчас / Пропустить»).
2. Если пропущено — Шаг 4 отображается как неактивный (Disabled), а на Шаге 5 отправляются только данные Шагов 1–3.
3. Если не пропущено — пользователь открывает разделы настроек, изменяет нужные параметры. Значения применяются на сервере только при завершении настройки на Шаге 5 (см. «Шаг 5. Завершение»), вместе с остальными данными.

---

## Flow 6. Логотип клиники

1. Пользователь на Шаге 1 загружает изображение логотипа.
2. Файл валидируется на клиенте (формат/размер), локально показывается предпросмотр (ссылка на файл, не закодированное содержимое).
3. Если файл не проходит клиентскую валидацию — отображается ошибка, переход к следующему шагу не блокируется (логотип необязателен), файл не принимается, пока пользователь не выберет корректный.
4. Файл уходит на сервер на Шаге 5 вместе с остальными данными. Если сервер не смог сохранить логотип, пользователь видит ошибку на Шаге 5 и может вернуться на Шаг 1, заменить или убрать логотип и повторить отправку.

---

# Шаг 1. Клиника

## Назначение

Ввод названия клиники и (опционально) её логотипа. Данные передаются в составе общего запроса инициализации (см. «Шаг 5. Завершение»).

## Поля

* Название клиники — обязательное текстовое поле.
* Логотип клиники — необязательная загрузка изображения (PNG, JPEG, SVG, WebP).

> Поля, связанные с подключением клиники по файлу/QR-коду и картой подтверждённых данных (название, тип лицензии, страна, статус подключения), **исключены** — такой механики нет в бэкенде. Идентификатор клиники на сервере компании (`clinic_id`) не вводится пользователем: он заполняется отдельным процессом провизионирования после инициализации и на этой странице никак не отображается и не редактируется.

---

# Шаг 2. Администратор

## Назначение

Ввод данных для создания роли (со всеми правами системы), должности и первого сотрудника-администратора. Все три сущности фактически создаются только при завершении настройки на Шаге 5, одним запросом.

## Поля

### Роль и должность

* Название роли (например, «Администратор») — этой роли на сервере присваиваются все права системы.
* Название должности — должность создаётся в отделе, который настраивается на Шаге 3.

### Данные сотрудника

* Логин
* Пароль
* Подтверждение пароля (сверяется только на клиенте, на сервер не отправляется)
* Имя
* Фамилия
* Отчество (опционально)
* Дата рождения
* Пол — список значений активного варианта стандарта «Пол» (см. «Источники данных для полей выбора»)
* Гражданство — код страны (ISO 3166-1 alpha-3)
* Страна проживания — код страны (ISO 3166-1 alpha-3)
* Регион проживания — код региона (ISO 3166-2)
* Адрес проживания (опционально)
* Тип занятости — «Сотрудник» или «Врач»
* Семейное положение — «Не в браке» / «В браке» / «Разведён(а)» / «Вдовец/вдова»

> **Изменение состава полей по сравнению с предыдущей версией документа:** поля «Email» и «Телефон» по-прежнему исключены — соответствующей логики на бэкенде нет и в актуальной схеме. При этом состав формы **расширен** по сравнению с прежней версией: добавлены название должности, дата рождения, пол, гражданство, страна и регион проживания, адрес, тип занятости и семейное положение — эти поля обязательны (кроме адреса) в схеме запроса инициализации бэкенда. Форму рекомендуется разбить на подгруппы (например, «Роль и должность», «Учётные данные», «Личные данные», «Проживание»), чтобы не перегружать пользователя одним длинным списком полей.

---

# Шаг 3. Адрес и график

## Назначение

Указание адреса клиники, региональных настроек и графика работы, а также создание первого (корневого) отдела. Данные фактически сохраняются только при завершении настройки на Шаге 5, одним запросом. Название отдела также используется как название типа отдела.

## Поля

### Основная информация

* Название первого отдела
* Страна — код страны (ISO 3166-1 alpha-3)
* Город
* Адрес
* Координаты на карте (широта и долгота) — задаются виджетом карты или вводом координат вручную

> Должность администратора создаётся именно в этом отделе, поэтому его название обязательно. Работа с несколькими филиалами в первом релизе не предусмотрена, название филиала не запрашивается.

### Региональные настройки

* Язык системы
* Часовой пояс

### Рабочий график

Расписание задаётся в виде диапазонов, а не индивидуально для каждого дня недели:

* Диапазон рабочих дней (например, «с понедельника по пятницу»)
* Диапазон рабочих часов (время открытия — время закрытия)

Дни, не входящие в выбранный диапазон, считаются выходными.

> Перерывы в мастере не настраиваются. При необходимости их можно добавить после первого входа в систему.

---

# Шаг 4. Настройки системы

## Назначение

Первичная, опциональная настройка глобальных параметров системы. Пользователь может пропустить этот этап целиком (настройки останутся значениями по умолчанию) либо пройти его — тогда изменённые параметры применяются в момент завершения настройки на Шаге 5 вместе с остальными данными (см. «Шаг 5. Завершение»).

## Переключатель «Настроить сейчас / Пропустить»

В начале Шага 4 отображается явный выбор:

* «Настроить сейчас» — открывает список разделов настроек.
* «Пропустить и настроить позже» — Шаг 4 сворачивается, соответствующий пункт степпера переходит в состояние Disabled, все изменения настроек сбрасываются, мастер сразу переходит к Шагу 5.

---

## Что настраивается на этом шаге

На шаге доступны **те же настройки, что и на странице «Глобальные настройки» после запуска** (`1.9.1`), — полный перечень с названиями, подсказками, значениями и значениями по умолчанию: `Global Settings Catalog.md` (папка `1.9.1. Global Settings Page`). Состав шага совпадает с составом страницы «Глобальные настройки»: новая настройка появляется на обеих страницах одновременно.

| Раздел | Настройки |
|---|---|
| Общие | Логотип клиники; Название клиники; Локализация системы; Часовой пояс |
| Структура | Сотрудник может иметь несколько рабочих мест |
| HR | Стандарт классификации пола; Норма ежегодного отпуска (дней); Обязательный первичный документ по кадровым движениям |
| ЭМК | Система измерения; Возраст совершеннолетия; Гражданство по умолчанию; Системы и группы крови; Категории инвалидности; Классификатор заболеваний; Типы родственных связей |
| Склад | Обязательный сопроводительный документ по операциям склада |
| Касса | Сотрудник регистратуры может быть кассиром |
| Бронирование | Один открытый визит на пациента |
| Услуги | Разрешить запись при нехватке расходников |

### Если шаг пропущен

* Все настройки остаются со **значениями по умолчанию**, поставляемыми с системой (см. каталог): например, отпуск — 28 дней, возраст совершеннолетия — 18 лет, классификатор заболеваний — МКБ-10, пол — «Упрощённый (М/Ж)», обязательные первичные документы в HR и на складе — включены, несколько сотрудников на одном рабочем месте — разрешены, запись при нехватке расходников — разрешена.
* Название клиники, логотип, язык и часовой пояс берутся из Шагов 1 и 3 — они сохраняются в любом случае.
* Позже все настройки можно изменить на странице «Управление клиникой → Глобальные настройки» (нужно право `MGMT_SETTINGS_MANAGE`, у первого администратора оно есть).

### Если шаг пройден

* Пользователь открывает нужные разделы и меняет настройки; неизменённые разделы остаются со значениями по умолчанию и не сохраняются отдельно.
* Раздел, в котором есть изменения, помечается точкой в левом списке; над списком показывается «Изменено разделов: N».
* Значения применяются на сервере только при нажатии «Завершить настройку» на Шаге 5; до этого их можно свободно менять.
* Предупреждения о последствиях показываются **информационной строкой** под настройкой, а не модальным окном (значения ещё не отправлены): «Кадровые движения будут применяться без сопроводительного документа» (при выключении обязательного документа в HR), «Операции склада будут выполняться без сопроводительного документа» (то же на складе), «Новые диагнозы будут выбираться из выбранного классификатора» (при смене классификатора заболеваний).

## Общий Layout

Шаг состоит из двух областей.

### Левая панель

Список разделов настроек. Разделы соответствуют внутренним модулям системы. Список:

* Общие
* Структура
* HR
* ЭМК
* Склад
* Касса
* Бронирование
* Услуги

Раздел без настроек (например, «Файлы», пока в нём нет настроек) не показывается.

Список должен поддерживать вертикальную прокрутку.

---

### Правая панель

Контент выбранного раздела. Содержит:

* Название раздела
* Список настроек

---

## Карточка настройки

Каждая настройка отображается отдельным блоком. Состав блока:

### Заголовок

Название настройки. Пример: Название клиники

---

### Описание

Краткое описание назначения настройки. Пример: Название организации, отображаемое в системе.

---

### Поле ввода

Тип зависит от конфигурации настройки.

---

### Ошибка валидации

Отображается под полем.

---

## Поддерживаемые типы настроек

### Text Input

Однострочное текстовое поле.

### Number Input

Поле для ввода чисел.

### Toggle / Checkbox

Переключатель Да / Нет.

### Select

Одиночный выбор значения из заранее заданного списка.

### Multi Select

Множественный выбор значений из заранее заданного списка.

### File Upload

Загрузка файла изображения.

### Remote Select

Список, значения которого подтягиваются из соответствующего модуля системы. **На этапе инициализации недоступен**: изменить такую настройку можно только после полной активации системы. Поле отображается как заблокированное, с пояснением «Доступно после завершения инициализации».

### Collection

Редактируемая таблица записей с возможностью вложенности (запись может содержать набор вложенных настроек с такой же структурой). Поддерживает:

* Добавление строки
* Удаление строки
* Редактирование строки

> **Типы «Text Area», «Date Picker» и «Time Picker» по-прежнему отсутствуют** в списке поддерживаемых типов настроек этого шага — соответствующей бизнес-логики для них на сервере не предусмотрено. (Поле «Дата рождения» на Шаге 2 — отдельный, специфичный для формы администратора элемент интерфейса, не связанный с системой типов настроек этого шага.)

## Раздел «General» — особый случай

В разделе «Общие» четыре настройки уже получены на предыдущих шагах и показываются **предзаполненными из состояния мастера**, повторный ввод не требуется:

| Настройка | Откуда предзаполнена |
|---|---|
| Логотип клиники | Шаг 1 (загруженный логотип; если не загружен — пусто) |
| Название клиники | Шаг 1 |
| Локализация системы | Шаг 3 (язык системы) |
| Часовой пояс | Шаг 3 (часовой пояс) |

Пользователь может изменить эти значения и здесь: введённое на Шаге 4 значение переопределяет значение с Шага 1/3 при финальной отправке. Состав и значения остальных разделов (Структура, HR, ЭМК, Склад, Касса, Бронирование) — значения по умолчанию из каталога.

## Кастомизация стандартов не поддерживается

> **Изменение по сравнению с предыдущей версией документа:** возможность создавать, редактировать и удалять собственные («кастомные») варианты справочников-стандартов (классификация пола, группы крови и т.д.) **полностью удалена из бизнес-логики бэкенда**. Клиника может только **выбрать один из вариантов**, поставляемых вместе с платформой. Соответственно из дизайна убраны: элемент «Управление вариантами», модальное окно со списком системных/кастомных вариантов, форма создания собственного варианта. Настройка-стандарт отображается как обычный `select` со списком вариантов — без какого-либо дополнительного элемента управления рядом с полем.

## Правила отображения

* Интерфейс должен поддерживать неограниченное количество разделов.
* Интерфейс должен поддерживать неограниченное количество настроек.
* Header, Stepper и Footer остаются фиксированными.
* Прокручивается только область контента.
* Изменение значения происходит без перезагрузки страницы и без немедленной отправки на сервер (кроме случаев, описанных выше для `Remote Select`, который на этом шаге недоступен для изменения в принципе).
* Каждая настройка отображает название и текущее значение.

# Шаг 5. Завершение

## Назначение

Финальный шаг, на котором происходит фактическое применение всех данных, введённых пользователем на предыдущих шагах.

## Порядок отправки данных

1. Отправляется единый запрос с данными Шагов 1–3 (клиника, логотип, адрес и график, отдел, роль, должность, администратор) и изменёнными настройками Шага 4 (если этап не пропущен).
   * При успехе сервер создаёт структуру клиники, отдел, роль, должность и учётную запись администратора одной транзакцией.
   * При ошибке на любом этапе этого запроса, включая недопустимое значение настройки, — **полный откат**: ни одна сущность не создаётся и ни одна настройка не сохраняется, система остаётся неинициализированной, пользователь возвращается к соответствующему шагу мастера с описанием ошибки и может повторить попытку, не теряя введённые данные.
## Экран ожидания

В момент нажатия «Завершить настройку» отображается индикатор процесса, информирующий пользователя о происходящем (без необходимости точного прогресс-бара по процентам), например, в виде последовательности этапов:

1. Создание клиники и отдела.
2. Создание роли, должности и администратора.
3. Применение настроек (только если этап настроек не был пропущен).

На этом экране элементы формы заблокированы, повторная отправка недоступна.

## Экран подтверждения (Success)

Отображается после успешного завершения запроса:

* Клиника и отдел созданы
* Администратор создан
* Настройки сохранены (если этап не был пропущен)

## Кнопка «Завершить настройку»

Активна только при отсутствии ошибок валидации на всех предыдущих шагах. После полностью успешного завершения превращается в кнопку перехода на страницу авторизации.

# Состояния

## Empty

* Данные отсутствуют.
* Следующий шаг недоступен.

---

## Loading

* Выполняется операция (загрузка схемы раздела настроек, либо завершение настройки на последнем шаге).
* Элементы формы заблокированы.
* Отображается индикатор выполнения.

---

## Error

Возможные причины ошибок, на которые должен реагировать интерфейс:

* Ошибка проверки данных (валидация полей) — на любом из Шагов 1–4.
* Ошибка при создании клиники/отдела/администратора при завершении настройки (Шаг 5, часть 1) — ни одна из этих сущностей не сохраняется, пользователь может повторить попытку, не теряя введённые данные.
* Ошибка, связанная с логотипом клиники (в составе общего запроса Шага 5) — отправка завершается ошибкой целиком; пользователь может вернуться на Шаг 1, убрать или заменить логотип (поле необязательно) и повторить отправку.
* Ошибка в значении настройки Шага 4 — отправка завершается ошибкой целиком, пользователь возвращается на Шаг 4 к соответствующей настройке.
* Ошибка валидации значения настройки (значение не входит в список допустимых) — отображается под соответствующим полем на Шаге 4.
* Попытка изменить настройку типа `Remote Select` до завершения инициализации — поле заблокировано и не может быть отправлено на сервер.
* Ошибка, если страница инициализации открыта повторно после того, как система уже была настроена — пользователь должен быть перенаправлен на страницу авторизации, мастер не показывается.

Сообщение должно содержать понятное описание проблемы.

* Активный шаг визуально выделяется.
* Ошибки отображаются без смещения интерфейса.
* Загрузка сопровождается индикатором прогресса.
* Завершение настройки сопровождается уведомлением об успехе .
* Все переходы между состояниями должны быть плавными и предсказуемыми.

# Acceptance Criteria

* Пользователь может пройти все этапы настройки в рамках одного мастера; данные Шагов 1–3 не применяются по отдельности — они отправляются одним запросом при завершении мастера.
* Логотип клиники не загружается на сервер отдельно — он передаётся в составе общего запроса на Шаге 5.
* Можно создать первого администратора с расширенным составом полей (роль, должность, учётные данные, личные данные, тип занятости, семейное положение) без email и телефона.
* Можно указать адрес клиники и первый отдел, с расписанием в виде диапазонов дней/часов (без перерывов). Поля «Название филиала» нет.
* Можно настроить системные параметры по разделам, либо пропустить этот этап целиком: без него система считается настроенной.
* Кастомизация вариантов справочников-стандартов недоступна — можно только выбрать один из предустановленных вариантов.
* Настройки типа `Remote Select` недоступны для изменения до завершения инициализации.
* Шаг 4 показывает те же разделы и настройки, что страница «Глобальные настройки» (`Global Settings Catalog.md`); при пропуске шага все настройки остаются со значениями по умолчанию.
* Раздел «Общие» на Шаге 4 предзаполнен значениями Шагов 1 и 3; изменённое значение переопределяет введённое ранее.
* Все обязательные поля проходят валидацию.
* При ошибке на Шагах 1–3 (единый запрос) — полный откат, без потери введённых пользователем данных в мастере.
* Состояния частичного успеха нет: либо сохраняется всё, либо ничего.
* После полностью успешного завершения настройки пользователь перенаправляется на страницу авторизации.
* Если система уже была настроена ранее, страница мастера не отображается — выполняется перенаправление на страницу авторизации.
