# 1.1.1. System Initialization Page

## Спецификация страницы интерфейса

* Название страницы: Инициализация системы
* Модуль: Management
* Тип страницы: Первичная настройка клиники
* Основные роли: Администратор клиники, Оператор клиники
* Статус документа: Актуализировано по документации бэкенда (ManagementModule, все этапы)
* Платформа: веб-приложение для медицинской системы

---

# Назначение страницы и сценарии использования

Страница предназначена для первоначальной настройки системы после установки. С помощью страницы пользователь может:

1. Указать название клиники и загрузить логотип.
2. Создать первого администратора системы (роль, должность, учётная запись сотрудника).
3. Настроить первый филиал и его первый отдел.
4. Настроить системные параметры (опционально — можно пропустить и настроить позже).
5. Завершить процесс активации системы.

После успешного завершения инициализации пользователь получает возможность авторизоваться и работать в системе.

**Важная особенность логики (соответствует бэкенду):** данные Шагов 1–3 (клиника, администратор, филиал) технически являются одним атомарным запросом на сервере — `POST /management/initialization`. Именно поэтому в мастере они собираются локально и отправляются на сервер одним запросом только в момент завершения этих трёх шагов (при переходе к Шагу 5). До этого момента пользователь может свободно возвращаться назад и менять любые введённые данные — ничего не считается окончательным. Если при создании возникает ошибка — сервер откатывает всё созданное в рамках этого запроса (транзакция), система остаётся неинициализированной, и пользователь может повторить попытку.

Шаг 4 (настройки системы) — **отдельный, опциональный** этап. Он не входит в основной запрос инициализации: каждый его раздел сохраняется собственным запросом на сервер. Пользователь либо явно пропускает этот этап целиком (тогда система активируется сразу после Шагов 1–3), либо проходит его — тогда изменения по разделам отправляются на сервер в момент нажатия «Завершить настройку» на Шаге 5 (см. «Шаг 5. Завершение»).

Логотип клиники — исключение из общей логики «всё отправляется одним запросом на Шаге 5»: в системе не используется base64-кодирование для передачи файлов, поэтому бинарный файл логотипа не может ехать внутри JSON-тела `POST /management/initialization` вместе с остальными данными. Для этого случая гвард сервера отдельно открывает ещё один эндпоинт до завершения инициализации — `POST /management/initialization/logo` (`multipart/form-data`): логотип загружается на сервер сразу при выборе файла на Шаге 1, а в основной запрос на Шаге 5 уходит только полученный `logo_id` (строка), а не сам файл.

# Layout страницы

Страница представляет собой полноэкранный мастер настройки (Wizard). Состоит из следующих областей:

## Header

Содержит:

* Название страницы
* Краткое описание текущего этапа
* Индикатор общего прогресса настройки

---

## Stepper

Расположен под Header.

Тип:

* Horizontal Stepper

Этапы:

1. Клиника
2. Администратор
3. Филиал
4. Настройки системы
5. Завершение

Состояния этапов:

* Completed
* Active
* Disabled
* Error

Пользователь всегда видит:

* текущий этап;
* завершённые этапы;
* общее количество этапов.

---

## Content Area

Основная рабочая область страницы. Отображает контент текущего шага. Контент может прокручиваться независимо от остальных элементов страницы.

---

## Footer

Закреплён в нижней части страницы. Содержит кнопки управления мастером:

* Назад
* Далее
* Завершить настройку

Правила:

* На первом шаге кнопка «Назад» скрыта.
* На промежуточных шагах отображаются кнопки «Назад» и «Далее».
* На последнем шаге отображается кнопка «Завершить настройку».
* Переход на следующий шаг невозможен при наличии ошибок валидации.
* Переход между шагами 1–4 не приводит к обращению к серверу (кроме безусловного чтения списка/схем разделов настроек на Шаге 4 — см. далее) — реальное создание сущностей происходит только на Шаге 5.

# User Flows

## Flow 1. Полная настройка системы

1. Пользователь открывает страницу.
2. Указывает название клиники и (опционально) логотип.
3. Создаёт администратора (роль, должность, данные сотрудника).
4. Создаёт первый филиал и отдел.
5. Настраивает параметры системы (или явно пропускает этот этап).
6. Завершает настройку — данные Шагов 1–3 отправляются одним запросом, затем (если не пропущено) настройки отправляются по разделам.
7. Получает доступ к авторизации — только когда система полностью инициализирована.

---

## Flow 2. Клиника и логотип

1. Пользователь вводит название клиники.
2. Опционально загружает изображение логотипа — файл валидируется на клиенте (тип, размер), затем сразу отправляется на сервер отдельным запросом (`POST /management/initialization/logo`, доступен уже на этом шаге, до общей отправки Шагов 1–3); локально хранится только ссылка на файл для предпросмотра.
3. Переход к следующему шагу заблокирован, пока загрузка логотипа не завершится (успехом или явным отказом от логотипа) — если пользователь не выбирал файл, шаг проходится без него.
4. Пользователь переходит к следующему шагу.

> **Изменение логики по сравнению с предыдущей версией документа:** сценарий с подключением клиники по конфигурационному JSON-файлу или QR-коду **удалён** — в схеме запроса инициализации бэкенда (`POST /management/initialization`) нет ни такого механизма, ни отдельного шага подтверждения подлинности клиники. Клиника создаётся напрямую из введённых пользователем названия и логотипа.

---

## Flow 3. Создание администратора

1. Пользователь вводит название роли и название должности.
2. Вводит данные сотрудника-администратора (см. «Шаг 2. Администратор»).
3. Переходит к следующему этапу. Роль, должность и учётная запись фактически создаются только при завершении настройки на Шаге 5.

---

## Flow 4. Настройка филиала

1. Пользователь указывает данные филиала и первого отдела.
2. Настраивает местоположение (страна, город, адрес, координаты на карте).
3. Настраивает расписание работы.
4. Подтверждает данные и переходит дальше. Филиал и отдел фактически создаются только при завершении настройки на Шаге 5.

---

## Flow 5. Настройка системы (опционально)

1. Пользователь решает, настраивать ли систему сейчас, или пропустить этап и настроить его позже, после первого входа в систему (переключатель «Настроить сейчас / Пропустить»).
2. Если пропущено — Шаг 4 отображается как неактивный (Disabled), а на Шаге 5 отправляется финальный запрос с флагом пропуска, после которого система сразу переходит в статус «инициализирована».
3. Если не пропущено — пользователь открывает разделы настроек, изменяет нужные параметры. Значения применяются на сервере только при завершении настройки на Шаге 5 (см. «Шаг 5. Завершение»), по одному запросу на каждый затронутый раздел.

---

## Flow 6. Логотип клиники

1. Пользователь на Шаге 1 загружает изображение логотипа.
2. Файл валидируется на клиенте (формат/размер), локально показывается предпросмотр (ссылка на файл, не закодированное содержимое).
3. Если файл не проходит клиентскую валидацию — отображается ошибка, переход к следующему шагу не блокируется (логотип необязателен), но загрузка не запускается, пока пользователь не выберет корректный файл.
4. Прошедший валидацию файл сразу отправляется на сервер (`POST /management/initialization/logo`) — переход к следующему шагу заблокирован до завершения этой загрузки; ошибка загрузки (`FILE_MODULE_ERROR` и т.п.) показывается тут же, на Шаге 1, а не откладывается до Шага 5.

---

# Шаг 1. Клиника

## Назначение

Ввод названия клиники и (опционально) её логотипа. Сущность клиники как таковая на сервере не создаётся отдельным запросом — данные передаются в составе общего запроса инициализации (см. «Шаг 5. Завершение»).

## Поля

* Название клиники — обязательное текстовое поле.
* Логотип клиники — необязательная загрузка изображения (PNG, JPEG, SVG, WebP).

> Поля, связанные с подключением клиники по файлу/QR-коду и картой подтверждённых данных (название, тип лицензии, страна, статус подключения), **исключены** — такой механики нет в бэкенде. Идентификатор клиники на сервере компании (`clinic_id`) не вводится пользователем: он заполняется отдельным процессом провизионирования после инициализации и на этой странице никак не отображается и не редактируется.

---

# Шаг 2. Администратор

## Назначение

Ввод данных для создания роли (со всеми правами системы), должности и первого сотрудника-администратора. Все три сущности фактически создаются только при завершении настройки на Шаге 5, одним запросом.

## Поля

### Роль и должность

* Название роли (например, «Администратор») — этой роли на сервере присваиваются все права системы.
* Название должности — должность создаётся в отделе, который настраивается на Шаге 3.

### Данные сотрудника

* Логин
* Пароль
* Подтверждение пароля (сверяется только на клиенте, на сервер не отправляется)
* Имя
* Фамилия
* Отчество (опционально)
* Дата рождения
* Пол — список значений активного варианта стандарта «Пол» (см. «Источники данных для полей выбора»)
* Гражданство — код страны (ISO 3166-1 alpha-3)
* Страна проживания — код страны (ISO 3166-1 alpha-3)
* Регион проживания — код региона (ISO 3166-2)
* Адрес проживания (опционально)
* Тип занятости — «Сотрудник» или «Врач»
* Семейное положение — «Не в браке» / «В браке» / «Разведён(а)» / «Вдовец/вдова»

> **Изменение состава полей по сравнению с предыдущей версией документа:** поля «Email» и «Телефон» по-прежнему исключены — соответствующей логики на бэкенде нет и в актуальной схеме. При этом состав формы **расширен** по сравнению с прежней версией: добавлены название должности, дата рождения, пол, гражданство, страна и регион проживания, адрес, тип занятости и семейное положение — эти поля обязательны (кроме адреса) в схеме запроса инициализации бэкенда. Форму рекомендуется разбить на подгруппы (например, «Роль и должность», «Учётные данные», «Личные данные», «Проживание»), чтобы не перегружать пользователя одним длинным списком полей.

---

# Шаг 3. Филиал

## Назначение

Создание первого филиала организации и его первого (корневого) отдела. Обе сущности фактически создаются только при завершении настройки на Шаге 5, одним запросом. Название отдела также используется как название типа отдела.

## Поля

### Основная информация

* Название филиала
* Название первого отдела
* Страна — код страны (ISO 3166-1 alpha-3)
* Город
* Адрес
* Координаты на карте (широта и долгота) — задаются виджетом карты или вводом координат вручную

> **Изменение по сравнению с предыдущей версией документа:** ранее отдел на этой странице не упоминался вовсе. По актуальной бизнес-логике бэкенда отдел создаётся вместе с филиалом в рамках одного и того же шага инициализации (должность администратора привязывается именно к этому отделу), поэтому его название добавлено как обязательное поле.

### Региональные настройки

* Язык системы
* Часовой пояс

### Рабочий график

Расписание задаётся в виде диапазонов, а не индивидуально для каждого дня недели:

* Диапазон рабочих дней (например, «с понедельника по пятницу»)
* Диапазон рабочих часов (время открытия — время закрытия)

Интерфейс сохраняет удобный для пользователя формат ввода (диапазон), но перед отправкой на сервер преобразует его в развёрнутый список из 7 дней недели, как того требует схема запроса инициализации (см. «Хранение и обновление состояния» в документации фронтенда). Дни, не входящие в выбранный диапазон, помечаются как выходные.

> **Перерывы исключены:** возможность добавить временные интервалы перерывов, присутствовавшая в предыдущей версии документа, **удалена** — в схеме запроса инициализации бэкенда для расписания филиала нет соответствующего поля. Если настройка перерывов необходима, она должна быть вынесена за пределы мастера инициализации и согласована отдельно как часть модуля Structure (после первого входа в систему).

# Шаг 4. Настройки системы

## Назначение

Первичная, опциональная настройка глобальных параметров системы. Пользователь может пропустить этот этап целиком (тогда система активируется сразу после Шагов 1–3) либо пройти его — тогда изменённые разделы применяются в момент завершения настройки на Шаге 5, каждый отдельным запросом к серверу (см. «Шаг 5. Завершение»).

## Переключатель «Настроить сейчас / Пропустить»

В начале Шага 4 отображается явный выбор:

* «Настроить сейчас» — открывает список разделов настроек.
* «Пропустить и настроить позже» — Шаг 4 сворачивается, соответствующий пункт степпера переходит в состояние Disabled, мастер сразу переходит к Шагу 5 с флагом пропуска настроек.

---

## Общий Layout

Шаг состоит из двух областей.

### Левая панель

Список разделов настроек. Разделы соответствуют интеграции с внутренними модулями системы, их состав и количество определяются сервером динамически. Примеры:

* General
* Structure module
* HR module
* EMC module

Список должен поддерживать вертикальную прокрутку.

---

### Правая панель

Контент выбранного раздела. Содержит:

* Название раздела
* Список настроек

---

## Карточка настройки

Каждая настройка отображается отдельным блоком. Состав блока:

### Заголовок

Название настройки. Пример: Название клиники

---

### Описание

Краткое описание назначения настройки. Пример: Название организации, отображаемое в системе.

---

### Поле ввода

Тип зависит от конфигурации настройки.

---

### Ошибка валидации

Отображается под полем.

---

## Поддерживаемые типы настроек

### Text Input

Однострочное текстовое поле.

### Number Input

Поле для ввода чисел.

### Toggle / Checkbox

Переключатель Да / Нет.

### Select

Одиночный выбор значения из статического списка, заданного сервером.

### Multi Select

Множественный выбор значений из статического списка, заданного сервером.

### File Upload

Загрузка файла изображения.

### Remote Select

Список, значения которого подтягиваются с REST API соответствующего модуля системы (а не статически заданы сервером в схеме). **На этапе инициализации недоступен**: сервер отклоняет попытку изменить такую настройку до полной активации системы. Поле отображается как заблокированное, с пояснением «Доступно после завершения инициализации».

### Collection

Редактируемая таблица записей с возможностью вложенности (запись может содержать набор вложенных настроек с такой же структурой). Поддерживает:

* Добавление строки
* Удаление строки
* Редактирование строки

> **Типы «Text Area», «Date Picker» и «Time Picker» по-прежнему отсутствуют** в списке поддерживаемых типов настроек этого шага — соответствующей бизнес-логики для них на сервере не предусмотрено. (Поле «Дата рождения» на Шаге 2 — отдельный, специфичный для формы администратора элемент интерфейса, не связанный с системой типов настроек этого шага.)

---

## Раздел «General» — особый случай

Часть настроек раздела General (логотип клиники, название клиники, язык, часовой пояс) дублирует данные, уже введённые пользователем на Шагах 1 и 3. Интерфейс должен отображать этот раздел с уже предзаполненными значениями из состояния мастера, не требуя повторного ввода. Изменение значения в этом разделе на Шаге 4 переопределяет значение, введённое ранее на Шаге 1/3, при финальной отправке.

---

## Кастомизация стандартов не поддерживается

> **Изменение по сравнению с предыдущей версией документа:** возможность создавать, редактировать и удалять собственные («кастомные») варианты справочников-стандартов (классификация пола, группы крови и т.д.) **полностью удалена из бизнес-логики бэкенда**. Клиника может только **выбрать один из вариантов**, поставляемых вместе с платформой. Соответственно из дизайна убраны: элемент «Управление вариантами», модальное окно со списком системных/кастомных вариантов, форма создания собственного варианта. Настройка-стандарт теперь отображается как обычный `select` со статически заданным списком вариантов — без какого-либо дополнительного элемента управления рядом с полем.

---

## Правила отображения

* Интерфейс должен поддерживать неограниченное количество разделов.
* Интерфейс должен поддерживать неограниченное количество настроек.
* Header, Stepper и Footer остаются фиксированными.
* Прокручивается только область контента.
* Изменение значения происходит без перезагрузки страницы и без немедленной отправки на сервер (кроме случаев, описанных выше для `Remote Select`, который на этом шаге недоступен для изменения в принципе).
* Каждая настройка отображает название и текущее значение.

# Шаг 5. Завершение

## Назначение

Финальный шаг, на котором происходит фактическое применение всех данных, введённых пользователем на предыдущих шагах.

## Порядок отправки данных

1. Отправляется единый запрос с данными Шагов 1–3 (клиника, филиал, отдел, роль, должность, администратор) и флагом «пропустить настройки» (в зависимости от выбора на Шаге 4).
   * При успехе сервер создаёт филиал, отдел, роль, должность и учётную запись администратора одной транзакцией.
   * При ошибке на любом этапе этого запроса — **полный откат**: ни одна сущность не создаётся, система остаётся неинициализированной, пользователь возвращается к соответствующему шагу мастера с описанием ошибки и может повторить попытку, не теряя введённые данные.
2. Если настройки не были пропущены — далее отправляется по одному запросу на каждый раздел настроек, изменённый на Шаге 4; последний из этих запросов помечается флагом финализации, который переводит систему в полностью инициализированное состояние.
   * Каждый раздел сохраняется независимо: ошибка в одном разделе не откатывает уже сохранённые разделы (см. «Экран частичного успеха»).

## Экран ожидания

В момент нажатия «Завершить настройку» отображается индикатор процесса, информирующий пользователя о происходящем (без необходимости точного прогресс-бара по процентам), например, в виде последовательности этапов:

1. Создание клиники, филиала и отдела.
2. Создание роли, должности и администратора.
3. Сохранение настроек по разделам (только если этап настроек не был пропущен).

На этом экране элементы формы заблокированы, повторная отправка недоступна.

## Экран подтверждения (Success)

Отображается только тогда, когда система полностью инициализирована (все обязательные и выбранные пользователем этапы завершены успешно):

* Клиника, филиал и отдел созданы
* Администратор создан
* Настройки сохранены (если этап не был пропущен)

## Экран частичного успеха

Возможна ситуация, когда Шаги 1–3 применены успешно (клиника, филиал, отдел, администратор созданы), но не все разделы настроек Шага 4 удалось сохранить. В этом случае:

* Отображается предупреждающий баннер с перечнем успешно и неуспешно сохранённых разделов.
* Доступна кнопка «Повторить», которая повторно отправляет запросы только для не сохранённых разделов.
* **Переход к авторизации недоступен**, пока не будут успешно сохранены все разделы и система не перейдёт в полностью инициализированное состояние — до этого момента сервер продолжает блокировать все запросы, включая авторизацию.

> **Изменение по сравнению с предыдущей версией документа:** ранее при частичном успехе переход к авторизации оставался доступен. По актуальной бизнес-логике бэкенда система остаётся заблокированной для всех операций (в том числе авторизации), пока флаг полной инициализации не выставлен в `true` — поэтому переход к авторизации при частичном успехе невозможен.

## Кнопка «Завершить настройку»

Активна только при отсутствии ошибок валидации на всех предыдущих шагах. После полностью успешного завершения превращается в кнопку перехода на страницу авторизации.

# Состояния

## Empty

* Данные отсутствуют.
* Следующий шаг недоступен.

## Loading

* Выполняется операция (загрузка схемы раздела настроек, либо завершение настройки на последнем шаге).
* Элементы формы заблокированы.
* Отображается индикатор выполнения.

---

## Error

Возможные причины ошибок, на которые должен реагировать интерфейс:

* Ошибка проверки данных (валидация полей) — на любом из Шагов 1–4.
* Ошибка при создании клиники/филиала/отдела/администратора при завершении настройки (Шаг 5, часть 1) — ни одна из этих сущностей не сохраняется, пользователь может повторить попытку, не теряя введённые данные.
* Ошибка, связанная с логотипом клиники (в составе общего запроса Шага 5) — не считается фатальной для остальных данных только в том смысле, что пользователь может вернуться на Шаг 1, убрать или заменить логотип (поле необязательно) и повторить отправку; сама отправка при этом всё равно завершается ошибкой целиком (см. «Порядок отправки данных»).
* Ошибка сохранения одного или нескольких разделов настроек на Шаге 5, часть 2 — приводит к экрану частичного успеха, а не к общей ошибке.
* Ошибка валидации значения настройки (значение не входит в список допустимых) — отображается под соответствующим полем на Шаге 4.
* Попытка изменить настройку типа `Remote Select` до завершения инициализации — поле заблокировано и не может быть отправлено на сервер.
* Ошибка, если страница инициализации открыта повторно после того, как система уже была настроена — пользователь должен быть перенаправлен на страницу авторизации, мастер не показывается.

Сообщение должно содержать понятное описание проблемы.

# Interaction & Animation

* Переключение между шагами происходит плавно.
* Активный шаг визуально выделяется.
* Ошибки отображаются без смещения интерфейса.
* Загрузка сопровождается индикатором прогресса.
* Завершение настройки сопровождается уведомлением об успехе (или предупреждением при частичном успехе).
* Все переходы между состояниями должны быть плавными и предсказуемыми.

# Acceptance Criteria

* Пользователь может пройти все этапы настройки в рамках одного мастера; данные Шагов 1–3 не применяются по отдельности — они отправляются одним запросом при завершении мастера.
* Логотип клиники не загружается на сервер отдельно и немедленно — он передаётся в составе общего запроса на Шаге 5.
* Можно создать первого администратора с расширенным составом полей (роль, должность, учётные данные, личные данные, тип занятости, семейное положение) без email и телефона.
* Можно создать первый филиал вместе с первым отделом, с расписанием в виде диапазонов дней/часов (без перерывов).
* Можно настроить системные параметры по разделам, либо явно пропустить этот этап целиком.
* Кастомизация вариантов справочников-стандартов недоступна — можно только выбрать один из предустановленных вариантов.
* Настройки типа `Remote Select` недоступны для изменения до завершения инициализации.
* Все обязательные поля проходят валидацию.
* При ошибке на Шагах 1–3 (единый запрос) — полный откат, без потери введённых пользователем данных в мастере.
* При частичном успехе (Шаги 1–3 успешны, часть разделов настроек — нет) переход к авторизации остаётся недоступен, пока все разделы не будут сохранены.
* После полностью успешного завершения настройки пользователь перенаправляется на страницу авторизации.
* Если система уже была настроена ранее, страница мастера не отображается — выполняется перенаправление на страницу авторизации.
