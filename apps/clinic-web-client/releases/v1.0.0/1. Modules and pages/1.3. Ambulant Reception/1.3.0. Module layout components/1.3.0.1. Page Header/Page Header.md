# Page Header

## Описание компонента

**Page Header** — заголовочный блок, расположенный в верхней части контентной области страницы на всю ширину. Компонент разделён на две части:

- **Левая часть**: заголовок страницы с названием текущей секции или модуля.
- **Правая часть**: две основные кнопки-триггеры для управления пациентами и их визитами.

---

## Кнопка «Зарегистрировать пациента»

Предназначена для создания новой записи пациента в системе.

### Task Flow

#### Этап 1. Инициация регистрации

1. Пользователь нажимает кнопку **Зарегистрировать пациента** в Header.
2. Открывается модальное окно регистрации.
3. Пользователь выбирает тип гражданства:
   - Гражданин Республики Узбекистан
   - Иностранный гражданин

#### Этап 2. Поиск существующего пациента

Над компонентом Tab располагается **поле для поиска** пациента с дебаунсингом:

- **Для граждан РУз**: поиск по PINFL или FaceID
- **Для иностранных граждан**: поиск по MRZ (Machine Readable Zone)

#### Этап 2.1. Захват документа: 1 или 2 изображения, 3 способа (панель распознавания)

Под полем поиска располагается **панель распознавания документа** — вместо единственной кнопки сканирования доступны **3 равнозначные кнопки** захвата изображения документа (паспорт/ID-карта/метрика):

1. **Сканировать документ** — захват через подключённый к рабочему месту документ-сканер (десктоп). Сканер должен возвращать файл **в формате изображения** (не PDF).
2. **Загрузить изображение** — загрузка готового файла (фото/скан) с компьютера или из галереи устройства.
3. **Сфотографировать документ** — захват через веб-камеру рабочего места (десктоп) либо через камеру устройства (планшет).

Выбор способа не влияет на дальнейшую логику — все три кнопки приводят к одному и тому же результату: изображение документа передаётся на бекенд Synapse, который пересылает его во внешний AI-сервис распознавания (MRZ) и возвращает уже распознанные поля. Фронтенд не обращается к AI-сервису напрямую.

**1 или 2 изображения.** Загранпаспорт умещает MRZ и все нужные данные на одном развороте — достаточно одного скана. Но пациент может предъявить документ с двумя информативными сторонами (ID-карта: лицевая сторона с фото/MRZ, обратная — с подписью и частью полей) — тогда сотрудник регистратуры сканирует/фотографирует/загружает документ **дважды**, по одному разу на каждую сторону, любым из трёх способов (стороны можно захватывать разными способами: например, сканером — лицо, камерой — оборот). Оба захвата выполняются **до отправки формы** (Этап 3–4), не позже.

**Task Flow панели:**

1. Сотрудник регистратуры выбирает один из трёх способов и захватывает первую сторону документа.
2. Система показывает индикатор загрузки/распознавания («Распознаём документ…») и отправляет изображение на бекенд Synapse (`POST /emc/passport/recognize`, один вызов на одно изображение).
3. При успехе — связанные поля автоматически заполняются (страна, гражданство, пол, ФИО, дата рождения, серия/номер документа, MRZ) в разделе «Персональные данные» (Этап 3).
4. Под превью первого скана появляется кнопка **«Добавить вторую сторону документа»** — опциональна; при нажатии открывает те же 3 способа захвата для второй стороны. Результат второго распознавания **объединяется** с первым: поля, пришедшие пустыми в первом ответе, заполняются из второго (например, MRZ — с лицевой стороны, часть адресных полей — с оборота); поля, заполненные в обоих ответах, не перезатираются вторым без явного действия оператора.
5. Фотография гражданина и графическая подпись с документа не извлекаются на этом шаге и не показываются оператору отдельными превью — они извлекаются backend-ом при финальной отправке формы (Этап 4), из объединённого backend-ом изображения одного или обоих сканов (§6.10.2 `EMCModule.md`).
6. Сотрудник **проверяет и при необходимости правит** автозаполненные поля вручную (обязательный шаг — MRZ/OCR может ошибаться, особенно на транслитерации имён).
7. Кнопка **«Очистить»** рядом с каждым превью документа — сбрасывает соответствующий загруженный скан (и, если это была единственная сторона, автозаполненные из него поля), возвращая форму в состояние ручного ввода (не затрагивает поля, которые оператор уже успел отредактировать вручную после автозаполнения — уточняется дизайном интеракций).
8. Кнопка **«Заполнить вручную»** — всегда доступна и пропускает распознавание; форма остаётся полностью пустой для ручного заполнения. Если ни одна сторона документа не была захвачена, оператор дополнительно загружает **фото пациента** и **графическую подпись пациента отдельными файлами** (см. Этап 3, «Фото пациента»), поскольку извлечь их из документа backend-у не из чего.

**Индикация результата распознавания:**

- Успех — превью загруженного документа (для каждой захваченной стороны) + toast «Данные распознаны»;
- MRZ не найден (документ без MRZ либо резервный сценарий ещё не готов) — toast «MRZ не найден, заполните данные вручную», форма остаётся пустой, это штатный случай, не ошибка;
- Ошибка AI-сервиса (недоступен, таймаут) — toast с ошибкой и кнопкой «Повторить», форма доступна для ручного заполнения без блокировки регистрации.

**Устройство ввода: десктоп vs планшет** (см. также §15a `EMCModule.md` и раздел «Планшетная версия» ниже в этом документе):

- **Десктоп** — «Сканировать документ» работает через интеграцию с подключённым сканером рабочего места (TWAIN/SANE/производитель-специфичный драйвер — интеграция на уровне ОС/десктоп-агента, не браузерный API; драйвер должен отдавать файл в формате изображения, не PDF); «Сфотографировать» — через веб-камеру рабочего места (`getUserMedia`).
- **Планшет** — кнопка «Сканировать документ» скрывается (внешнего сканера нет); доступны только «Сфотографировать» (камера самого планшета) и «Загрузить изображение» (файл/галерея планшета). Обе стороны документа (если их две) захватываются этими же способами.

#### Этап 3. Заполнение данных пациента

Форма содержит три раздела, доступные через компонент **Tab**:

##### **Раздел 1: Персональные данные** (обязательно)

- **MRZ паспорта** (опционально) — автозаполняется при сканировании
- **Идентификационный номер/Серия паспорта** (опционально)
  - Поддерживаемые типы: номер/серия паспорта, загран. паспорта, метрика
- **Ф.И.О** (обязательно) — три отдельных инпута: фамилия, имя, отчество
  - Отчество опционально
- **Дата рождения** (обязательно)
- **Опекун / законный представитель** (обязательно **только** для несовершеннолетнего пациента — появляется динамически, см. Этап 3.1 ниже)
- **Пол** (обязательно)
- **Страна** (обязательно)
- **Город/Провинция** (обязательно)
- **Адрес** (обязательно для граждан РУз, опционально для иностранцев)
- **Контактная информация** (минимум 1)
  - Тип: номер телефона, почта, социальная сеть
  - Значение: номер, адрес почты, ссылка на профиль
- **Фото пациента** (опционально; **обязательно**, если ни одна сторона документа не была отсканирована/сфотографирована на Этапе 2.1 — загружается отдельным файлом взамен фото, которое иначе извлекается из скана)
- **Графическая подпись пациента** (опционально; **обязательно**, если ни одна сторона документа не была отсканирована/сфотографирована на Этапе 2.1 — загружается отдельным файлом-изображением взамен подписи, которая иначе извлекается из скана; служит эталоном для последующей сверки при подписании соглашения ПДн, Этап 5)
- **Категория пациента** (опционально) — выбор из предопределённого списка

##### Этап 3.1. Поле «Опекун / законный представитель» — несовершеннолетний пациент

Логика синхронизирована с бэкендом (`EMCModule.md` §6.12, `PatientIdentityService`) — фронтенд не изобретает собственное правило совершеннолетия, а воспроизводит серверную проверку для мгновенной обратной связи оператору, финальное решение всегда остаётся за сервером.

1. При каждом изменении поля **«Дата рождения»** форма пересчитывает возраст пациента и сравнивает его с пороговым значением **`emc.adult_age`** — глобальной настройкой Management Module (`GET /management/settings/...`, значение по умолчанию `18`, то же значение, которым пользуется сервер при валидации, §6.12 `EMCModule.md`).
2. Если возраст **меньше** `emc.adult_age` — под полем «Дата рождения» появляется поле **«Опекун / законный представитель»** и становится **обязательным** (нельзя перейти к Этапу 4, не заполнив его). Если возраст **больше или равен** порогу — поле скрыто и не требуется (может быть заполнено добровольно через альтернативный сценарий — см. `relatives`, вне текущего поля).
3. Поле реализовано как **поиск с автодополнением** (аналог поиска пациента на Этапе 2) — ввод ФИО, MRN или ПИНФЛ ищет среди уже зарегистрированных пациентов клиники: `GET /emc/patients?search=...` (§12.1 `EMCModule.md`). В выпадающем списке отображаются: ФИО, MRN, дата рождения — чтобы отличить полных тёзок.
4. Оператор выбирает нужного пациента — в поле сохраняется его `id`, который на Этапе 5 уходит в форму как `guardian_patient_id` (обязательное поле `CreatePatientDto`, §16.1 `EMCModule.md`).

###### Если ЭМК опекуна ещё не существует

5. Под полем поиска — кнопка **«Создать ЭМК опекуна»**. Она открывает **вложенную модаль регистрации нового пациента** — точно ту же форму (Этапы 1–6 этого документа, включая распознавание документа, панель захвата, три раздела данных и подписание соглашения ПДн), что и обычная регистрация, но запущенную поверх текущей (незавершённой) регистрации несовершеннолетнего.
6. Форма несовершеннолетнего пациента при этом **не теряется** — её черновик сохраняется в фоне, пока открыта вложенная модаль.
7. После успешного создания ЭМК опекуна (включая, при необходимости, подписание его собственного соглашения ПДн — Этап 5) вложенная модаль закрывается, и оператор возвращается к форме несовершеннолетнего пациента.
8. Поле **«Опекун / законный представитель»** в форме несовершеннолетнего **автоматически заполняется** только что созданным пациентом (по возвращённому `id` из ответа `POST /emc/patients` вложенной регистрации) — повторный поиск не требуется.
9. Оператор может вручную очистить это автозаполненное значение (кнопка **«Изменить»**/крестик в поле) и выбрать другого опекуна через поиск (п. 3), если, например, ошибочно создал не того человека.

###### Edge cases: поле опекуна

- **У пациента уже указан возраст-пограничное значение** (ровно `emc.adult_age` лет) — считается совершеннолетним (строгое неравенство «меньше», см. §6.12 `EMCModule.md`), поле не требуется.
- **Оператор меняет дату рождения так, что пациент из несовершеннолетнего становится совершеннолетним** — поле «Опекун» скрывается, но уже выбранное значение не сбрасывается автоматически (на случай возврата к прежней дате); при отправке формы пустое необязательное поле не блокирует сабмит.
- **Оператор меняет дату рождения в обратную сторону** (пациент становится несовершеннолетним после того, как уже был указан как совершеннолетний) — поле «Опекун» появляется заново и требует заполнения до перехода к Этапу 4.
- **Опекуном пытаются указать самого пациента** (актуально при редактировании через `1.3.2. Patient EMC Card`) — сервер отклоняет `422 PATIENT_GUARDIAN_INVALID`; фронтенд также исключает текущего пациента (по MRZ/ПИНФЛ уже введённым в форме) из результатов поиска на клиенте как первый рубеж.
- **Выбранный опекун был архивирован** между поиском и отправкой формы — сервер вернёт `404 PATIENT_GUARDIAN_NOT_FOUND`; поле подсвечивается как невалидное, оператору предлагается выбрать другого опекуна или создать нового (см. Обработку ошибок фронтенд-документации, `1.3.1. Patients Registry` §4).
- **Поиск не находит ни одного пациента** — под полем показывается «Ничего не найдено» и кнопка «Создать ЭМК опекуна» (п. 5) остаётся доступной как основной путь.
- **Вложенная регистрация опекуна прервана/закрыта без сохранения** — поле «Опекун» в форме несовершеннолетнего остаётся пустым, оператор может повторить попытку.

##### **Раздел 2: Физиологические данные** (полностью опционально)

- **Рост**
- **Вес**
- **Индекс массы тела** — рассчитывается автоматически на основе роста и веса
- **Группа крови**

##### **Раздел 3: Особые данные** (полностью опционально)

- **Хронические заболевания**
- **Инвалидность**
- **Аллергии**

#### Этап 4. Проверка дубликатов

5. После заполнения формы система **автоматически выполняет поиск дубликатов**.
   - Поиск выполняется перед финальным подтверждением регистрации.

#### Этап 5. Подпись соглашения об обработке ПДн

6. Если дубликаты не найдены, форма (Раздел 1–3, Этап 3) отправляется — `POST /emc/patients` создаёт ЭМК (§6.10.4 `EMCModule.md`). Изображение документа, переданное в этот запрос, становится **обязательным**: без него (`passport_scan` и, если было захвачено, `passport_scan_back` — либо готовые `passport_photo`/`graphic_sign_photo`, загруженные вручную) регистрация не завершается — это отличие от прежней версии дизайна, где скан был опционален. Оба скана (если их два) и/или ручные фото/подпись передаются в этом же запросе — все изображения собираются на Этапе 2.1/3, второй этап регистрации новых изображений уже не запрашивает.
7. Сразу после создания ЭМК открывается модаль **«Согласие об обработке персональных данных»** (см. полный юридический текст документа: `synapse-architecture-documentation/.../2.1.0. EMC module/Personal Data Processing Agreement (PDPA) Template.md`) — это **второй этап** оформления пациента.

##### 5.1 Выбор способа подписания → запрос на бекенд

- Модаль сначала предлагает оператору выбрать способ получения подписи — **«На бумаге»** либо **«На планшете»** (стилус/палец) — и только после выбора запрашивает документ у бекенда: `GET /emc/patients/:id/pdpa/render`, где `:id` — id только что созданного пациента, а параметр `format` соответствует выбору:
  - **«На бумаге»** → `?format=pdf` — сразу PDF с подставленными данными пациента, место подписи пусто (для печати).
  - **«На планшете»** → `?format=html` (по умолчанию) — HTML с теми же данными и служебной меткой на месте подписи; на превью в модали метка визуально заменяется пустой областью подписи.
- Превью соглашения показывает текст с уже подставленными значениями пациента (ФИО, дата рождения, адрес, название клиники и филиала, дата, сотрудник регистратуры) независимо от выбранного способа.

##### 5.2 Способ «На бумаге» → печать → повторный захват (3 кнопки)

1. Оператор выбирает **«На бумаге»** — система запрашивает `?format=pdf` и открывает системное окно печати браузера/ОС.
2. Документ печатается на принтере рабочего места.
3. Пациент подписывает документ на бумаге собственноручно и отдаёт его сотруднику регистратуры.
4. Модаль подписания переходит в состояние **«Оцифруйте подписанный документ»** — те же **3 кнопки** захвата, что и на Этапе 2.1, но в контексте уже подписанного бумажного документа:
   - **Сфотографировать документ** (веб-камера/камера планшета);
   - **Загрузить документ** (файл);
   - **Отсканировать документ** (подключённый сканер, десктоп-версия; сканер должен вернуть файл в формате изображения).
5. После захвата **уже полностью подписанный документ целиком** (текст соглашения + подпись на одном изображении) отправляется на бекенд: `POST /emc/patients/:id/pdpa` (`file`, `source: "scan" | "photo" | "upload"`) — сохраняет документ как есть и **автоматически** запускает сверку подписи через Sign-AI относительно эталонной подписи пациента (`graphic_sign_photo`, извлечённой на Этапе 2.1/3) — см. `EMCModule.md` §9.8.2–§9.9.
6. Кнопка **«Очистить»** рядом с превью загруженного скана соглашения — сбрасывает загруженный файл, позволяя переснять/перезагрузить заново без повторной печати.

##### 5.3 Способ «На планшете» (графическая подпись)

1. Оператор выбирает **«На планшете»** — система запрашивает `?format=html`, модаль показывает превью документа с областью подписи на месте служебной метки (`{{ sign__picture__1 }}`, см. шаблон соглашения); пациент/оператор расписывается стилусом/пальцем — на десктопе также мышью/тачпадом или через подключённый HID-планшет для подписи, на планшетном клиенте — прямо по экрану.
2. **Синхронно с процессом подписи** превью документа отображает уже нанесённые штрихи в реальном времени (canvas поверх превью, без задержки на сервер) — пациент/оператор видят, как формируется подпись, до завершения.
3. По завершении (кнопка **«Готово»**/поднятие пера дольше N сек — уточняется UX) штрихи рендерятся в изображение подписи (PNG, прозрачный фон). Фронтенд отправляет на бекенд **это изображение подписи вместе с HTML**, полученным на шаге 5.1: `POST /emc/patients/:id/pdpa` (`file` = PNG подписи, `html` = текст, полученный от `render`, `source: "digital_signature"`) — **бекенд**, а не фронтенд, вставляет изображение подписи в HTML на месте метки, рендерит итоговый PDF, сохраняет его как документ соглашения и **автоматически** запускает ту же сверку подписи через Sign-AI, что и в сценарии 5.2 (§9.8.3, §9.9). Это отличие от прежней версии контракта, где фронтенд сам собирал подписанный документ на клиенте.
4. Кнопка **«Очистить подпись»** — доступна пока штрихи ещё не отправлены; стирает canvas и позволяет расписаться заново без повторного открытия модали.

##### 5.4 Результат сверки и завершение

8. Если сверка (§9.9) вернула `decision: "match"` — соглашение помечается `is_verified: true` автоматически, модаль закрывается, показывается toast «Соглашение подписано и проверено».
9. Если `decision: "uncertain"` либо Sign-AI недоступен (`502 AI_SERVICE_ERROR`) — соглашение сохраняется как есть (`is_verified: false`), оператору показывается предупреждение «Не удалось автоматически подтвердить подпись» с кнопками **«Подтвердить вручную»** / **«Переснять/переподписать»**. Регистрация при этом **не блокируется** — см. п. 10 ниже.
10. Если `decision: "not_match"` — предупреждение «Подпись не совпадает с образцом в документе», предлагается переснять документ или переподписать; оператор может подтвердить вручную при явной уверенности (например, известная деформация подписи из-за травмы руки).
11. Сотрудник регистратуры может **завершить регистрацию без загрузки соглашения** и оформить его позже в ЭМК пациента (кнопка **«Пропустить, подписать позже»** в модали).
12. **ЭМК пациента, в котором нет верифицированного (`is_verified: true`) соглашения об обработке ПД, не может быть использована для записи на визит ни в одной клинике** — кнопка «Запись пациента к врачу» доступна, но сервер отклонит создание визита (`422 PATIENT_PDPA_NOT_VERIFIED`, `EMCModule.md` §9.2, §9.3, §9.8). Сама ЭМК (просмотр, редактирование персональных данных, дозагрузка файлов) при этом доступна без ограничений — это изменение по сравнению с прежним правилом «1 сутки, только текущая клиника», которое снято.

#### Этап 6. Завершение регистрации

13. После подписания соглашения (или явного пропуска, п. 11):
    - Система подтверждает регистрацию.
    - ЭМК пациента считается зарегистрированной — становится доступным немедленное создание записи на услугу (кнопка «Запись пациента к врачу», открывающая тот же поток, что и ниже в этом документе, уже с найденным пациентом).

#### Сценарии блокировки

14. Подтверждение регистрации (создание ЭМК, `POST /emc/patients`) блокируется в следующих случаях:
    - Обнаружен дубликат пациента в системе (`409 PATIENT_ALREADY_EXISTS`).
    - Не приложено ни одного изображения документа личности и не загружены вручную фото/подпись пациента (теперь обязательно, п. 6).
    - В обоих случаях показывается **Toast-уведомление** об ошибке, регистрация не выполняется.
15. Модаль подписания соглашения (Этап 5) **не блокирует** завершение регистрации — ЭМК уже создана к моменту её открытия (п. 6–7); лимит **10 минут** на подписание из предыдущей версии дизайна снят, так как несёт риск повторного визита в очередь ради простой печати документа. Взамен действует более строгое ограничение: **запись на визит к врачу невозможна**, пока соглашение не верифицировано (п. 12) — сама ЭМК при этом не ограничена.

#### Edge cases: подпись соглашения

- **Пациент отказывается подписывать** — оператор нажимает «Пропустить, подписать позже» (п. 11); ЭМК создана, но запись на визит заблокирована — см. п. 12.
- **Печать не удалась** (нет бумаги, принтер офлайн) — toast с ошибкой печати и предложением подписать способом «На планшете» (§5.3) вместо повторной попытки печати.
- **Веб-камера/сканер недоступны или не подключены** — соответствующая кнопка недоступна (disabled) с подсказкой при наведении «Устройство не обнаружено»; доступные способы остаются активными.
- **Пациент подписывает, но случайно закрывает вкладку/обновляет модаль до отправки** — незавершённый canvas-набросок не сохраняется; при повторном открытии модали область подписи пуста, требуется расписаться заново.
- **Повторная попытка после `not_match`/`uncertain`** — новый файл загружается через `PUT /emc/patients/:id/pdpa/:pdpaId`, полностью замещая предыдущий и запуская сверку заново (не создаёт вторую запись соглашения).
- **Двое сотрудников одновременно открывают модаль подписания для одного пациента** (редкий кейс, несколько окон регистратуры) — сервер принимает первую успешную загрузку; вторая попытка получает актуальное состояние (`is_verified`) при следующем открытии карточки.

### Планшетная версия сайта — как выглядит

На планшетном клиенте (сенсорный экран, без подключённого стационарного оборудования) весь процесс воспроизводится теми же экранами, но источники устройств переопределяются на встроенные возможности самого планшета:

| Функция десктоп-версии | Аналог на планшете |
|---|---|
| Сканер документов (Этап 2.1, 1 или 2 стороны) | Недоступен — кнопка «Сканировать документ» скрыта; остаются «Сфотографировать» (встроенная камера) и «Загрузить изображение», в т.ч. для второй стороны документа |
| Веб-камера рабочего места (Этап 2.1, 5.2) | Встроенная камера планшета (то же самое приложение съёмки, без внешнего устройства) |
| Принтер (Этап 5.2, способ «На бумаге») | Способ «На бумаге» доступен, если к планшету подключён (Bluetooth/Wi-Fi) принтер регистратуры; если печать физически невозможна на конкретном рабочем месте — способ скрывается по feature-флагу филиала, остаётся только «На планшете» |
| Отдельный планшет для подписи со стилусом (Этап 5.3, способ «На планшете») | Отдельная кнопка не нужна — сам планшетный клиент **является** этим планшетом: выбор способа «На планшете» сразу открывает область подписи на весь экран, ввод — пальцем или стилусом планшета напрямую по стеклу |
| Захват после печати (Этап 5.2, 3 кнопки) | Те же «Сфотографировать» / «Загрузить» доступны; «Отсканировать» скрыта по той же причине, что и в Этапе 2.1 |

Дополнительно для планшетной версии:

- Область подписи (§5.3) занимает большую часть экрана в портретной/альбомной ориентации, чтобы обеспечить комфортный росчерк пальцем — это не уменьшенная копия десктоп-виджета, а отдельный полноэкранный режим модали.
- Кнопки капчи документа (Этап 2.1, 5.2) укрупнены под тач-таргет (минимум 44×44px) и расположены с увеличенными отступами по сравнению с десктоп-версией.
- Ориентация экрана не блокируется — модаль подписи адаптируется к повороту устройства пациентом при подписании.

## Кнопка «Запись пациента к врачу»

Предназначена для создания новой записи (визита) пациента к врачу.

### Task Flow

#### Этап 1. Инициация записи

1. Пользователь нажимает кнопку **Запись пациента к врачу** в Header.
2. Открывается модальное окно создания визита пациента.

#### Этап 2. Поиск пациента

3. Пользователь ищет пациента по:
   - Ф.И.О
   - ID пациента
   - PINFL
   - FaceID
   - QR-код
   - MRZ (если пациент — иностранный гражданин)

#### Этап 3. Обработка активных визитов

4. Система показывает **активные незавершённые визиты** пациента в клинику (если они существуют).

5. **Если выбран активный визит**:
   - Разблокируются формы визита к врачу
   - Разблокируется загрузка файлов

6. **Если активного визита нет или нужен новый**:
   - Визит в клинику формируется **автоматически** на основе данных из первого визита к врачу
   - Разблокируются формы визита к врачу
   - Разблокируется загрузка файлов

#### Этап 4. Заполнение формы визита

Пользователь заполняет **форму визита к врачу** с интеллектуальной фильтрацией:

- **Степень срочности (Триаж)** (обязательно)
  - Выбор из предопределённого списка приоритетов

- **Направление** (опционально)
  - При выборе направления — список врачей автоматически фильтруется под это направление
  - Влияет на доступный список врачей

- **Врач** (обязательно)
  - При выборе врача — направление подставляется автоматически на основе специальности врача
  - Влияет на доступный список услуг

- **Услуга** (обязательно)
  - После выбора врача список услуг фильтруется
  - Содержит только те услуги, которые может предоставить выбранный врач

- **Дата и время** (необязательно)
  - Выбор даты и времени визита к врачу (букинг)
  - Если не указывается система создаёт запись в ближайшее свободное время в графике приёмов

#### Этап 5. Сохранение записи

8. Пользователь сохраняет запись — визит к врачу создаётся в системе
