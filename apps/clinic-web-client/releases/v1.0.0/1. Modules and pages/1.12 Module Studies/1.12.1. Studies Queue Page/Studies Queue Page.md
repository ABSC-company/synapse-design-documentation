# 1.12.1. Studies Queue Page

## Спецификация страницы интерфейса

- Страница: Очередь исследований
- Модуль: Исследования (лабораторные/инструментальные) — единственная страница модуля
- Позиция в модуле: Единственная (главная и единственная страница)
- Тип страницы: Рабочая очередь + создание медицинского документа
- Основные роли: Лаборант, сотрудник кабинета инструментальных исследований (в терминах `EMCModule.md` §5.5 — «эксперт (лаборатория / инструментальные исследования)»)
- Статус документа: Draft
- Связанная бэкенд-документация: `BookingModule.md` §4.2, §6.13, §12.3 (источник очереди — та же логика, что у `1.3.3. Booking`, читающего записи из Booking Module, а не из ЭМК); `EMCModule.md` §6.13, §9.5, §9.7, §12.5–12.6 (создание/привязка медицинского документа, файлы-приложения — клиническая часть по-прежнему в ЭМК); `HRModule.md` §15.4 (кабинеты, к которым привязан сотрудник, — `EmployeeWorkplaceDto.room`); `StructureModule.md` §5.8 (кабинеты); `EDMModule.md` (создание/подписание медицинского документа)

## Назначение страницы и сценарии использования

Единственный рабочий экран сотрудника кабинета лабораторных/инструментальных исследований. Не дублирует «Визиты к врачу» (`1.11.1. Doctor Visits Page`) — вместо визитов к конкретному врачу показывает **список визитов, записанных на кабинет** (`room_id`, а не `doctor_id`, см. §6.13 `EMCModule.md`/`BookingModule.md`). Источник очереди — **Booking Module**, а не ЭМК: та же логика разграничения, что уже принята для `1.3.3. Booking` (`1.3.0 Overview` §2 frontend-документации регистратуры) — букинг/расписание/занятость кабинета принадлежит Booking Module, ЭМК читается только там, где важна именно клиническая история. Сотрудник смотрит запись, чтобы понять, какую услугу реализовать (какой анализ/исследование провести), а затем — сразу либо позже (когда результат не готов моментально, типично для лабораторных исследований) — создаёт медицинский документ с описанием результатов (уже в ЭМК, через привязку `emc_visit_id`) и, при необходимости, прикрепляет файлы-приложения (снимки, распечатки анализатора и т.д.).

Ключевые задачи страницы:

1. Показать очередь визитов, записанных на кабинет(ы) сотрудника, на выбранную дату.
2. Дать понять по каждой записи, какая услуга должна быть реализована и для какого пациента.
3. Обеспечить поиск по **id записи визита** — то же значение, которым маркируются образцы для лабораторных исследований (пробирки, контейнеры), — а также по ФИО/MRN пациента.
4. Создать медицинский документ с результатами исследования, привязанный к визиту.
5. Прикрепить файлы-приложения к медицинскому документу (снимки, PDF с результатами анализатора и т.п.).
6. Показать, что документ уже создан/подписан по визиту — без повторного дублирования работы.

## User Flows / Task Flows для страницы

### Flow 1. Просмотр очереди

1. Сотрудник открывает страницу «Очередь исследований».
2. Система определяет **кабинеты, к которым сотрудник привязан** — не произвольный выбор из всех кабинетов филиала, а строго рабочие места этого сотрудника: `GET /hr/employees/:id` (свой профиль) → `workplaces[].room` (`HRModule.md` §15.4). У сотрудника может быть больше одного рабочего места и, соответственно, больше одного кабинета (например, совмещает УЗИ и рентген) — это ограничение видимости, а не просто предзаполнение поля.
3. По умолчанию таблица показывает очередь **сразу по всем кабинетам сотрудника** за выбранную дату (по умолчанию — сегодня): `GET /booking/visits-by-services?room_id={все кабинеты сотрудника}&date_from=&date_to=` (`BookingModule.md` §12.3 — `room_id` принимает несколько значений через запятую).
4. Если сотрудник привязан больше чем к одному кабинету — фильтр «Кабинет» (не селектор из всего филиала, а переключатель **среди своих** кабинетов) позволяет сузить очередь до одного конкретного, когда нужно сосредоточиться на нём; «Все мои кабинеты» — исходное состояние по умолчанию.
5. Каждая строка показывает: id записи, время, пациента, услугу, кабинет (если очередь показывает несколько кабинетов сразу), статус, наличие медицинского документа.
6. Сотрудник может переключить дату (сегодня/выбор из календаря) — список перезагружается.

> Кабинет — не редактируемая пользователем настройка этой страницы, а следствие назначения рабочих мест сотруднику в HR Module (административная операция, вне этой страницы). Если сотруднику назначен неверный кабинет — это исправляется в HR-карточке сотрудника, а не здесь.

### Flow 2. Поиск

1. Строка поиска над таблицей принимает **либо** id записи визита (число — точное совпадение, используется в т.ч. для быстрого поиска по номеру, которым промаркирован физический образец), **либо** ФИО/MRN пациента (частичное совпадение).
2. Система определяет тип ввода автоматически (число → поиск по id; иначе → поиск по пациенту) и подсвечивает, по какому критерию ищет.
3. Поиск по id **не ограничен выбранным кабинетом/датой** — если сотрудник ищет по номеру с образца, а запись относится к другому кабинету/дню (ошибка выбора фильтра оператором либо запись создана ранее), результат всё равно находится и показывается с явной пометкой «вне текущего фильтра» плюс кнопкой «Перейти» (сбрасывает кабинет/дату на значения найденной записи).
4. Пустой ввод — возвращает обычную очередь по текущему фильтру (Flow 1).

### Flow 3. Просмотр записи — что реализовать

1. Клик по строке открывает панель/модаль деталей визита: пациент (ФИО, дата рождения, MRN — минимально необходимое для идентификации, без полной ЭМК), услуга (наименование, из `service_snapshot`), кабинет, дата/время, статус.
2. Явно показывается **id записи** крупным шрифтом с кнопкой «Скопировать» — для переноса на маркировку физического образца.
3. Если по визиту уже есть медицинский документ(ы) — показывается их список (статус: черновик/подписан) со ссылкой на просмотр/продолжение заполнения.

### Flow 4. Создание медицинского документа с результатами

1. Из панели деталей (Flow 3) — кнопка **«Создать документ с результатами»**; доступна, только если визит уже привязан к реальной ЭМК (`emc_visit_id` заполнен в ответе Booking Module, см. Edge cases) — без ЭМК документировать результат некуда.
2. Открывается стандартный редактор документа EDM Module (`module: "medical_documents"`, `context: { patient_id }`) — выбор шаблона (или бланк без шаблона), заполнение результатов исследования.
3. После создания документ автоматически привязывается к визиту **в ЭМК** — по `emc_visit_id` из записи Booking, а не по `id` самой записи Booking (`POST /emc/service-visits/:id/medical-documents`, где `:id = emc_visit_id`, `EMCModule.md` §9.5).
4. В редакторе доступна загрузка файлов-приложений — снимки, PDF-выгрузки анализатора и т.п. (`POST /emc/patients/:id/files` с `medical_document_id`, `EMCModule.md` §9.7).
5. Документ можно сохранить как черновик и вернуться позже (типичный случай для лабораторных исследований, где результат готов не сразу) — статус визита при этом остаётся как есть (`paid`/`processing`), пока документ не подписан.
6. При подписании документа визит автоматически переходит в `completed` (`EMCModule.md` §9.5, «Подписание документа врачом → визит `completed`» — правило действует независимо от роли подписанта, не только врача, см. открытый вопрос ниже).

### Flow 5. Возврат к отложенному результату

1. Визит, по которому результат ещё не готов, остаётся в очереди (Flow 1) в статусе `paid`/`processing`, без подписанного документа — визуально отличим бейджем «Ожидает результата».
2. Сотрудник возвращается к нему позже (в т.ч. на следующий день — фильтр по дате не должен скрывать такие визиты, если они не завершены, см. Edge cases) и продолжает/завершает документ (Flow 4).

Общий layout страницы:

1. Слева: Sidebar в свёрнутом состоянии.
2. Сверху: **Page Header** — «Очередь исследований», фильтр «Кабинет» (среди своих), селектор даты.
3. Контентная область: Toolbar (поиск) + таблица очереди + панель деталей визита (drawer при выборе строки).

## Визуал: High-Fidelity mockups

Визуальные правила:

1. ID записи — визуально акцентирован (крупнее обычного текста таблицы, моноширинный шрифт) — это не просто технический идентификатор, а рабочий номер, на который смотрит сотрудник при маркировке образца.
2. Статус «Ожидает результата» — отдельный, узнаваемый цвет (например, синий), отличный от стандартного `processing`-жёлтого в остальной системе, — подчёркивает, что это нормальное промежуточное состояние для лабораторных исследований, а не задержка/проблема.
3. Строки с готовым, но неподписанным документом (черновик) визуально отличаются от строк вообще без документа — например, дополнительная иконка «черновик».
4. Найденная поиском по id запись вне текущего фильтра — отдельный, визуально выделенный блок над таблицей (не строка внутри неё), чтобы не перепутать с элементами обычной очереди.

Визуальные компоненты, обязательные к отрисовке в mockups:

1. Toolbar с фильтром «Кабинет» (среди своих), селектором даты и поиском.
2. Таблица очереди с разными статусами (ожидает результата / подписан / отменён).
3. Панель деталей визита.
4. Редактор медицинского документа, открытый из панели деталей (переиспользуется общий компонент EDM Module, не новый экран).
5. Блок «найдено вне текущего фильтра» (Flow 2, п. 3).
6. Состояние loading (skeleton таблицы).
7. Состояние empty (нет визитов на выбранный кабинет/дату).

## Состояния и edge cases

| Состояние | Ожидаемое поведение |
|---|---|
| loading | Skeleton таблицы |
| empty | Нет визитов по кабинетам сотрудника/дате — «Очередь пуста», без CTA (это штатное состояние, не ошибка) |
| error | Ошибка загрузки — сообщение + «Повторить» |
| offline | Создание/подписание документа недоступно, очередь — только просмотр из кэша |
| permissions | Страница скрыта без права на просмотр записей по услугам в Booking Module (`BOOKING_VISIT_SERVICE_GET`); кнопка создания документа скрыта без права создания медицинского документа (`EMC_MEDICAL_DOCUMENT_CREATE`) |

### Edge cases

1. У сотрудника нет ни одного рабочего места с кабинетом (структурная аномалия/сотрудник ещё не назначен на рабочее место) — очередь пуста с отдельным, отличным от обычного empty, сообщением: «Вам не назначен кабинет — обратитесь к администратору», без общего пустого состояния «на сегодня записей нет». Здесь система намеренно **не** предлагает выбрать произвольный кабинет филиала — доступ ограничен назначением, а не удобством.
2. Визит записан через предварительную запись (`prospective_patient`, без ЭМК ещё) и не привязан к реальному пациенту — `emc_visit_id = null` в ответе Booking Module. Строка отображается в очереди (услугу нужно провести физически независимо от статуса ЭМК), но кнопка «Создать документ с результатами» в панели деталей задизейблена с подсказкой «Свяжите визит с ЭМК в регистратуре, прежде чем создавать документ» — привязка предварительной записи к ЭМК (`BookingModule.md` §6, сценарии 7–8) выполняется в регистратуре, не на этой странице.
3. Сотрудник привязан к нескольким кабинетам (например, совмещает УЗИ и рентген) — очередь по умолчанию показывает оба сразу (с колонкой «Кабинет» в таблице для различения), фильтр позволяет сузить до одного.
4. Визит с отложенным результатом (Flow 5) не должен исчезать из очереди при смене даты на «сегодня», если он относится к вчерашнему дню и всё ещё не завершён — фильтр по дате учитывает не только `date` визита, но и **отсутствие подписанного документа**: незавершённые визиты прошлых дат показываются в отдельном блоке «Незавершённые» либо через явный фильтр «Показать незавершённые за все даты» (детали — на усмотрение реализации, здесь фиксируется только необходимость такого пути, чтобы результаты не терялись из виду).
5. По одному визиту уже есть подписанный документ, но сотрудник по ошибке пытается создать ещё один — система не блокирует (несколько документов на визит технически допустимы), но выводит предупреждение «По этому визиту уже есть подписанный документ — уверены, что нужен ещё один?».
6. Поиск по id визита, которого не существует — «Запись не найдена».
7. Поиск по id визита, который **найден, но относится к кабинету, к которому сотрудник не привязан** — трактуется как «не найдено», без утечки данных чужого кабинета (доступ по-прежнему ограничен назначением сотрудника, а не только UI-фильтром — см. открытый вопрос ниже о серверной проверке).
8. Поиск по id, который относится к визиту другого филиала/клиники (при многофилиальной установке) — трактуется как «не найдено» в контексте текущего филиала, без утечки данных другого филиала.
9. Визит отменён (`canceled`) после того, как сотрудник уже открыл панель деталей — при попытке создать документ показывается ошибка «Визит отменён», кнопка создания скрывается, панель обновляется.
10. Файл-приложение не загрузился (сетевая ошибка) — стандартная обработка редактора EDM Module, вне специфики этой страницы.

## Interaction & Animation

1. Смена кабинета/даты — таблица перезагружается с skeleton-состоянием, без полной перезагрузки страницы.
2. Поиск — debounce 300ms, автоматическое определение типа запроса (id/ФИО) без переключателя, который нужно щёлкать вручную.
3. Открытие панели деталей — slide-in справа (drawer), 300ms, тот же паттерн, что и в остальной системе.
4. Открытие редактора документа — переход в стандартный флоу EDM Module (не новая анимация, переиспользуется существующий паттерн).
5. После подписания документа — toast «Документ подписан, визит завершён», строка визита в очереди обновляется точечно (статус → `completed`) без полной перезагрузки таблицы.

## Зависимости и ограничения

### API

1. `GET /hr/employees/:id` (свой профиль) — `workplaces[].room` даёт список кабинетов сотрудника (`HRModule.md` §15.4); это единственный источник ограничения очереди, отдельного запроса к Structure Module не требуется.
2. `GET /booking/visits-by-services?room_id=&date_from=&date_to=&status=&id=` — очередь визитов и точный поиск по id; `room_id` принимает список кабинетов сотрудника через запятую (`BookingModule.md` §12.3), как и `1.3.3. Booking` для своего шедулера.
3. `GET /booking/visits-by-services?patient_search=` — поиск по ФИО/MRN пациента одним запросом (`BookingModule.md` §12.3).
4. `POST /edm/documents` + `POST /emc/service-visits/:id/medical-documents` (`:id = emc_visit_id` из ответа Booking) — создание и привязка медицинского документа (`EMCModule.md` §9.5).
5. `POST /emc/patients/:id/files` (`medical_document_id`) — файлы-приложения (`EMCModule.md` §9.7).

### Роли и права

1. `BOOKING_VISIT_SERVICE_GET` — просмотр очереди (Booking Module).
2. `EMC_MEDICAL_DOCUMENT_CREATE` — создание документа.
3. `EMC_MEDICAL_DOCUMENT_LINK_MANAGE` — привязка документа к визиту (выполняется автоматически при создании, скрытый шаг для пользователя).
4. `EMC_PATIENT_FILE_MANAGE` — загрузка файлов-приложений.
5. `EMC_PATIENT_GET` — не требуется для самой очереди (пациент приходит вместе с записью из Booking Module, §12.3), но нужен, если редактор документа дополнительно подгружает что-то из карточки пациента — уточнить при реализации.

> Подтверждено: правило «подписание документа → визит `completed`» (`EMCModule.md` §6.7, §9.5) роль-агностично — переход в `completed` срабатывает по подписанию **любым** сотрудником из очереди подписания документа (в т.ч. лаборантом/сотрудником кабинета инструментальных исследований), а не только ролью «врач».
>
> ⚠️ Открытый вопрос к бэкенду: `BOOKING_VISIT_SERVICE_GET` (`BookingModule.md` §9) — общее право просмотра всех записей по услугам, без привязки к конкретному кабинету/сотруднику. Ограничение очереди «только мои кабинеты» на этой странице сейчас реализуется **только фильтром на клиенте** (`room_id` из своего HR-профиля), а не серверным правом — держатель `BOOKING_VISIT_SERVICE_GET` технически может запросить `GET /booking/visits-by-services?room_id=<чужой>` напрямую и получить визиты чужого кабинета. Для ролей регистратуры/администратора это осознанно и корректно (им нужен доступ ко всем кабинетам), но для роли «лаборант/сотрудник кабинета» стоит решить, требуется ли отдельное, более узкое право с серверной проверкой принадлежности кабинета, или ограничение остаётся чисто UI-уровня по решению продукта.

### Технические ограничения

1. Таблица очереди не требует пагинации в типичном объёме (один кабинет, один день — как правило, десятки записей, не тысячи); при необходимости — стандартная пагинация системы.

## Acceptance criteria

1. Страница по умолчанию показывает очередь визитов по всем кабинетам, к которым привязан сотрудник, за выбранную дату.
2. Фильтр «Кабинет» ограничен только кабинетами самого сотрудника (из HR-профиля), не всем списком кабинетов филиала; скрыт, если у сотрудника ровно один кабинет.
3. Поиск работает как по id записи визита (точное совпадение, в т.ч. вне текущего фильтра кабинета/даты), так и по ФИО/MRN пациента.
4. ID записи визита визуально акцентирован и легко копируется — предназначен для маркировки образцов.
5. Из панели деталей визита доступно создание медицинского документа с результатами, привязанного к визиту.
6. К медицинскому документу можно прикрепить файлы-приложения.
7. Визит с неподписанным документом («ожидает результата») не теряется из очереди при смене даты.
8. Подписание документа автоматически переводит визит в статус `completed`.
9. Все состояния (loading/empty/error/offline/permissions) реализованы согласно таблице выше.
