# 1.11.3. Department Warehouse Page

## Спецификация страницы интерфейса

- Страница: Склад отделения
- Модуль: Врач (амбулаторный приём)
- Позиция в модуле: Третья страница
- Тип страницы: Мини-склад + запросы на пополнение
- Основные роли: Врач (амбулаторный приём)
- Статус документа: Draft
- Связанная бэкенд-документация: `WarehouseModule.md` §4.15–4.17, §7 (сценарий 3), §8.4, §9, §12.6–12.7

> Эта страница концептуально идентична `1.13.2. Department Warehouse Page` модуля «Сестринский персонал» — тот же потребительский склад отделения, те же данные. Разница только в наборе доступных действий: врач видит остатки и может создавать запросы на пополнение; сестринский модуль дополнительно даёт списание (см. `1.13.2`, а также раздел «Роли и права» ниже).

## Назначение страницы и сценарии использования

«Мини-склад» отделения — потребительский склад (`storages.type = "consumer"`, привязанный к `department_id` врача, `WarehouseModule.md` §4.15) с текущими остатками расходных материалов и инструментов, а также запросами на его пополнение с главного склада клиники. Врач видит, что есть в наличии в его отделении прямо сейчас, и может запросить пополнение, не выходя из врачебного модуля в отдельный модуль склада.

Ключевые задачи страницы:

1. Показать текущие остатки склада отделения.
2. Показать историю запросов на пополнение и их статусы.
3. Создать новый запрос на пополнение с указанием товаров и количества.

## User Flows / Task Flows для страницы

### Flow 1. Просмотр остатков

1. Врач открывает страницу «Склад отделения».
2. Система определяет склад отделения врача — через департамент его основной должности (`HRModule.md`, `position.department`) и `GET /warehouse/storages?type=consumer&department_id=` (`WarehouseModule.md` §12.6).
3. Таблица остатков: товар, текущее количество (`stock_summary` из `StorageResponseDto`).
4. Поиск/фильтр по названию товара.

### Flow 2. Создание запроса на пополнение

1. Кнопка **«Запросить пополнение»** открывает форму: выбор товаров (мультивыбор из каталога) и запрашиваемого количества по каждому.
2. Отправка создаёт запрос: `POST /warehouse/storage-requests { storage_id, items: [{ product_id, requested_quantity }] }` (`WarehouseModule.md` §12.7, статус `created`).
3. Запрос появляется в списке «Мои запросы» со статусом `created`.

### Flow 3. Просмотр статуса запросов

1. Вкладка/раздел «Мои запросы» — список запросов этого склада: `GET /warehouse/storage-requests?storage_id=` (`WarehouseModule.md` §12.7).
2. Статусы: `created` (создан) → `in_progress`/`approved` (обрабатывается складом) → `fulfilled` (выдан, остатки склада отделения обновлены) либо `rejected` (отклонён, с причиной).
3. Клик по запросу — детали: запрошенное количество по каждой позиции, одобренное количество (если уже обработан), причина отказа (если отклонён).

Общий layout страницы:

1. Слева: Sidebar в свёрнутом состоянии.
2. Сверху: **Page Header** — «Склад отделения», кнопка «Запросить пополнение».
3. Контентная область: Tab-меню («Остатки» / «Мои запросы»).

| Колонка | Описание |

- Для каждого выбранного — поле «Количество».
- Кнопка «Отправить запрос».

## Визуал: High-Fidelity mockups

Визуальные правила:

1. Остатки с низким количеством (ниже условного порога, если такой вводится клиникой) — визуально выделены (жёлтый/красный), чтобы врач видел, что скоро понадобится пополнение — если такой порог не задан в системе, эта деталь не отрисовывается (не изобретать несуществующее поле).
2. Статус запроса — та же цветовая палитра, что и статусы в остальной системе (жёлтый — в процессе, зелёный — выдан, красный — отклонён).

Визуальные компоненты, обязательные к отрисовке в mockups:

1. Tab-меню «Остатки» / «Мои запросы».
2. Таблица остатков.
3. Таблица запросов с разными статусами.
4. Модаль создания запроса.
5. Детали отклонённого запроса (с причиной).
6. Состояние loading/empty.

## Состояния и edge cases

| Состояние | Ожидаемое поведение |
|---|---|
| loading | Skeleton таблиц |
| empty | Остатков нет / запросов нет — соответствующее пустое состояние |
| error | Ошибка загрузки — сообщение + «Повторить» |
| offline | Создание запроса недоступно, просмотр — из кэша |
| permissions | Кнопка «Запросить пополнение» скрыта без `WAREHOUSE_STORAGE_REQUEST_CREATE`; страница скрыта без `WAREHOUSE_STORAGE_GET` |

### Edge cases

1. У врача не определён склад отделения (должность без привязки к отделу либо у отдела нет потребительского склада) — страница показывает сообщение «Склад вашего отделения не найден — обратитесь к администратору» вместо таблиц.
2. Запрос частично одобрен (одобренное количество меньше запрошенного по позиции) — в деталях запроса это видно построчно, без отдельного статуса на уровне всего запроса.
3. Повторная отправка похожего запроса, пока предыдущий не обработан — система не блокирует (дубли — это ответственность обрабатывающего кладовщика, не UI-ограничение).

## Interaction & Animation

1. Переключение вкладок — cross-fade, 200ms.
2. Создание запроса — модаль fade-in/out, стандартный паттерн системы.
3. После отправки запроса — toast «Запрос отправлен», переключение на вкладку «Мои запросы» с новой строкой.

## Зависимости и ограничения

### API

1. `GET /warehouse/storages?type=consumer&department_id=` — склад отделения с остатками.
2. `GET /warehouse/products?search=` — каталог товаров для выбора в запросе.
3. `POST /warehouse/storage-requests` — создание запроса.
4. `GET /warehouse/storage-requests?storage_id=` — список запросов.

### Роли и права

1. `WAREHOUSE_STORAGE_GET` — просмотр остатков.
2. `WAREHOUSE_STORAGE_REQUEST_CREATE` — создание запроса на пополнение.
3. `WAREHOUSE_STORAGE_REQUEST_GET` — просмотр своих запросов.

> Врачебная роль **не** получает `WAREHOUSE_MARKING_CODE_MANAGE` (списание) и `WAREHOUSE_STORAGE_REQUEST_PROCESS` (обработка чужих запросов) — эти права остаются за складом/сестринским персоналом (см. `1.13.2. Department Warehouse Page`).
>
> ⚠️ Открытый вопрос к бэкенду: определение «склада моего отделения» для врача идёт через department его основной должности (`HRModule.md`, `position.department`) → `GET /warehouse/storages?department_id=`. Прямого роута «мой склад» нет — аналогичный открытый вопрос уже зафиксирован для кабинетов в `1.12.1. Studies Queue Page`.

## Acceptance criteria

1. Страница показывает остатки склада отделения врача.
2. Врач может создать запрос на пополнение с указанием товаров и количества.
3. Статус запроса отслеживается на отдельной вкладке.
4. Все состояния (loading/empty/error/offline/permissions) реализованы согласно таблице выше.
