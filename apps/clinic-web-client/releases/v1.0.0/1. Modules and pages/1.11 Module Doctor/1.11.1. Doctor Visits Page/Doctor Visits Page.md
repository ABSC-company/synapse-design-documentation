# 1.11.1. Doctor Visits Page

## Спецификация страницы интерфейса

- Страница: Визиты к врачу
- Модуль: Врач (амбулаторный приём)
- Позиция в модуле: Первая страница — точка входа
- Тип страницы: Рабочая очередь
- Основные роли: Врач (амбулаторный приём)
- Статус документа: Draft
- Связанная бэкенд-документация: `BookingModule.md` §4.2, §6.13, §12.3 (источник очереди — та же логика, что у `1.3.3. Booking` и `1.12.1. Studies Queue Page`: расписание/букинг из Booking Module, а не из ЭМК); `EMCModule.md` §6.13, §9.5 (медицинские документы визита, доступны из `1.11.2. Consultation Page`)

## Назначение страницы и сценарии использования

Первый экран, который врач видит после входа в модуль — список визитов, записанных к нему на приём (`services.type = "consultation"`, `doctor_id`, см. §6.13 `BookingModule.md`/`EMCModule.md`). Не электронная очередь с вызовом пациента (это отдельная функциональность `1.3.6 Electronic Queue`, компонент интегрируется, а не переизобретается здесь) — просто рабочий список визитов на день с переходом в консультацию.

Ключевые задачи страницы:

1. Показать список визитов, записанных к врачу, на выбранную дату.
2. Дать быстрый переход в консультацию по визиту.
3. Показать статус визита (записан/оплачен/идёт приём/завершён/отменён/возврат).
4. Обеспечить поиск по пациенту (ФИО/MRN) и по id записи визита.

## User Flows / Task Flows для страницы

### Flow 1. Просмотр очереди

1. Врач открывает страницу «Визиты к врачу».
2. Таблица загружает визиты, записанные к этому врачу, за выбранную дату (по умолчанию — сегодня): `GET /booking/visits-by-services?doctor_id={я}&date_from=&date_to=` (`BookingModule.md` §12.3).
3. Каждая строка показывает: время, пациента, услугу, статус.
4. Врач может переключить дату (сегодня/выбор из календаря).

### Flow 2. Поиск

1. Строка поиска принимает id записи визита (точное совпадение) либо ФИО/MRN пациента (частичное совпадение) — то же автоопределение типа ввода, что в `1.12.1. Studies Queue Page` Flow 2.
2. Поиск по id не ограничен датой — находит визит вне текущего фильтра с явной пометкой и кнопкой перехода.

### Flow 3. Переход в консультацию

1. Клик по строке визита в статусе `paid`/`processing` открывает `1.11.2. Consultation Page` для этого визита.
2. Клик по визиту в статусе `reservation` (запись создана, не оплачена) открывает превью визита без возможности начать приём — с подсказкой «Пациент ещё не оплатил визит».
3. Клик по визиту в статусе `completed`/`canceled`/`refunded` открывает консультацию в режиме только чтения (просмотр уже внесённых данных/документов).

Общий layout страницы:

1. Слева: Sidebar в свёрнутом состоянии.
2. Сверху: **Page Header** — «Визиты к врачу», селектор даты.
3. Контентная область: Toolbar (поиск) + таблица визитов.

## Визуал: High-Fidelity mockups

Визуальные правила:

1. Статус-бейджи — единая палитра со всей системой (см. `1.3.0 Overview` §6.1).
2. Визиты в статусе `processing` (идёт приём) визуально выделены (например, левая цветная полоса) — врач должен быстро найти, где приём уже начат, но не завершён (например, вернулся к списку по ошибке).
3. Строка визита без возможности начать приём (`reservation`) визуально приглушена относительно доступных для приёма.

Визуальные компоненты, обязательные к отрисовке в mockups:

1. Toolbar с датой и поиском.
2. Таблица визитов с разными статусами.
3. Блок «найдено вне текущего фильтра даты» (поиск по id).
4. Состояние loading (skeleton).
5. Состояние empty (нет визитов на выбранную дату).

## Состояния и edge cases

| Состояние | Ожидаемое поведение |
|---|---|
| loading | Skeleton таблицы |
| empty | Нет визитов на выбранную дату — «На сегодня визитов нет» |
| error | Ошибка загрузки — сообщение + «Повторить» |
| offline | Список — только просмотр из кэша, переход в консультацию заблокирован |
| permissions | Страница скрыта без права на просмотр записей по услугам (`BOOKING_VISIT_SERVICE_GET`) |

### Edge cases

1. Визит перешёл в `paid` пока врач смотрел список (оплата на кассе параллельно) — статус обновляется точечно без перезагрузки всей таблицы (если реализован live-обновление) либо при следующем рефетче.
2. Поиск по id визита другого врача — визит находится (право на просмотр общее, см. открытый вопрос ниже), но переход в консультацию для чужого визита недоступен — только просмотр карточки визита, без права редактирования/подписания.
3. Пациент отменил визит (`canceled`) — строка остаётся в списке дня с соответствующим статусом, не исчезает (врач должен видеть, что приём не состоится).

## Interaction & Animation

1. Смена даты — таблица перезагружается со skeleton-состоянием.
2. Поиск — debounce 300ms.
3. Клик по строке — переход на `1.11.2. Consultation Page` (полная навигация, не модаль — приём достаточно объёмный процесс для отдельной страницы).

## Зависимости и ограничения

### API

1. `GET /booking/visits-by-services?doctor_id=&date_from=&date_to=&status=&id=&patient_search=` — очередь и поиск (`BookingModule.md` §12.3).

### Роли и права

1. `BOOKING_VISIT_SERVICE_GET` — просмотр очереди.

> ⚠️ Открытый вопрос к бэкенду (тот же, что и в `1.12.1. Studies Queue Page`): `BOOKING_VISIT_SERVICE_GET` не разграничивает «мои визиты» от визитов любого другого врача — держатель права технически может запросить чужой `doctor_id`. Для роли «врач» стоит решить, требуется ли ограничение видимости чужих визитов на уровне сервера, или это остаётся продуктовым решением (врач с этим правом и так может выполнять административные функции регистратуры в некоторых клиниках).

## Acceptance criteria

1. Страница показывает визиты, записанные к текущему врачу, за выбранную дату.
2. Поиск работает по id визита (вне фильтра даты) и по ФИО/MRN пациента.
3. Переход в консультацию доступен только для визитов в статусе `paid`/`processing`.
4. Все состояния (loading/empty/error/offline/permissions) реализованы согласно таблице выше.
