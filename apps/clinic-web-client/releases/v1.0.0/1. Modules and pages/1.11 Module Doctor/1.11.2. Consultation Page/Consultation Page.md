# 1.11.2. Consultation Page

## Спецификация страницы интерфейса

- Страница: Консультация
- Модуль: Врач (амбулаторный приём)
- Позиция в модуле: Вторая страница — открывается из «Визиты к врачу»
- Тип страницы: Рабочий экран приёма + документооборот
- Основные роли: Врач (амбулаторный приём)
- Статус документа: Draft
- Связанная бэкенд-документация: `BookingModule.md` §12.3 (`emc_visit_id` — связь на визит в ЭМК); `EMCModule.md` §6.13, §9.5, §9.7, §12.5–12.6 (медицинские документы визита, файлы-приложения); `EDMModule.md` (документооборот — тот же общий паттерн, что и в остальных модулях системы)

## Назначение страницы и сценарии использования

Рабочий экран одного визита — открывается из `1.11.1. Doctor Visits Page`. Врач видит минимальный клинический контекст пациента и работает с медицинскими документами визита: создаёт новый документ по результатам приёма либо открывает/дополняет уже существующие. Полная история болезни пациента (предыдущие визиты, диагнозы, документы за всё время) — не на этой странице, а в общей карточке пациента (`1.3.2. Patient EMC Card`), куда есть прямая ссылка.

Ключевые задачи страницы:

1. Показать контекст визита — пациент, услуга, дата/время.
2. Дать доступ к клиническим данным, важным во время приёма (аллергии, хронические заболевания) — сводно, без перехода в полную ЭМК.
3. Показать документооборот визита — список документов, привязанных к этому визиту, тем же общим паттерном, что и в остальных модулях системы (EDM Module).
4. Дать возможность создать новый медицинский документ по визиту.
5. Ссылка на полную ЭМК пациента (`1.3.2. Patient EMC Card`) для случаев, когда нужен более широкий контекст.

## User Flows / Task Flows для страницы

### Flow 1. Открытие консультации

1. Врач переходит на страницу из `1.11.1` (визит в статусе `paid`/`processing`).
2. Шапка страницы показывает: ФИО пациента, возраст, аллергии и хронические заболевания (всегда на виду, выделены цветом) — сводка из `GET /emc/patients/:id` (минимальный набор полей, не полная карта).
3. Отображается блок услуги: наименование, дата/время визита.
4. Загружается список медицинских документов визита: `GET /emc/service-visits/:id/medical-documents` (`:id = emc_visit_id` из записи Booking, `EMCModule.md` §12.6) — тот же общий компонент списка документов, что используется в остальных модулях (папки/статусы/поиск, EDM Module).

### Flow 2. Создание медицинского документа

1. Кнопка **«Создать документ»** открывает стандартный редактор документа EDM Module (`module: "medical_documents"`, `context: { patient_id }`) — выбор шаблона (заключение, справка и т.п.) или бланк без шаблона.
2. После создания документ автоматически привязывается к визиту (`POST /emc/service-visits/:id/medical-documents`, `EMCModule.md` §9.5).
3. Документ можно сохранить как черновик и вернуться позже.

### Flow 3. Работа с уже существующими документами визита

1. Клик по документу в списке (Flow 1, п. 4) открывает его в редакторе EDM Module — просмотр/правка (пока не подписан), подписание.
2. Подписание документа переводит визит в `completed` автоматически (`EMCModule.md` §6.7, §9.5) — правило роль-агностично: подписантом может быть врач либо любой другой уполномоченный сотрудник из очереди подписания шаблона.

### Flow 4. Переход в полную ЭМК

1. Кнопка **«ЭМК пациента»** в шапке — переход на `1.3.2. Patient EMC Card` этого пациента (вся история визитов/документов за всё время, не только текущий визит).

Общий layout страницы:

1. Слева: Sidebar в свёрнутом состоянии.
2. Сверху: **Page Header** — «Консультация», ФИО пациента, кнопка «Назад к списку визитов», кнопка «ЭМК пациента».
3. Контентная область: шапка клинического контекста (аллергии/хронические) + блок услуги + список документов + кнопка «Создать документ».

## Визуал: High-Fidelity mockups

Визуальные правила:

1. Аллергии — красный/оранжевый акцент, всегда видны без скролла (та же логика, что в старой версии модуля — критично для безопасности пациента).
2. Список документов — тот же визуальный паттерн, что списки документов в других модулях (HR, Warehouse) — единообразие документооборота по системе.
3. Статус документа (черновик/подписан) — те же цветовые обозначения, что в EDM Module в целом.

Визуальные компоненты, обязательные к отрисовке в mockups:

1. Шапка с аллергиями/хроническими заболеваниями.
2. Блок визита.
3. Список документов (пустой и с документами разных статусов).
4. Редактор документа, открытый из этой страницы (переиспользуется общий компонент EDM Module).
5. Состояние loading, empty (нет документов по визиту).

## Состояния и edge cases

| Состояние | Ожидаемое поведение |
|---|---|
| loading | Skeleton шапки и списка документов |
| empty | Документов по визиту ещё нет — «Документов пока нет» + кнопка «Создать документ» |
| error | Ошибка загрузки — сообщение + «Повторить» |
| offline | Создание/редактирование документа недоступно |
| permissions | Кнопка «Создать документ» скрыта без `EMC_MEDICAL_DOCUMENT_CREATE`; список документов скрыт без `EMC_MEDICAL_DOCUMENT_GET` |

### Edge cases

1. Визит ещё не привязан к ЭМК (крайне маловероятно для консультации, но теоретически возможно для предварительной записи, `emc_visit_id = null`, см. `BookingModule.md` §4.2) — блок документооборота недоступен с сообщением «Визит не привязан к ЭМК — свяжите в регистратуре», кнопка «Создать документ» скрыта.
2. Визит отменён (`canceled`) после открытия консультации — страница переходит в режим только чтения, создание документа блокируется.
3. У пациента нет аллергий/хронических заболеваний — блок не показывает пустые бейджи, просто отсутствует эта часть шапки (не «Нет данных», а отсутствие визуального шума).
4. Документ уже подписан другим сотрудником (например, консультация велась совместно) — открывается в режиме просмотра, не редактирования.

## Interaction & Animation

1. Открытие редактора документа — переход в стандартный флоу EDM Module.
2. После подписания документа — toast «Документ подписан», список документов и статус визита обновляются точечно.
3. Кнопка «Назад к списку визитов» возвращает на `1.11.1` без потери позиции прокрутки/фильтров (дата, поиск).

## Зависимости и ограничения

### API

1. `GET /emc/patients/:id` — минимальные клинические данные (аллергии, хронические заболевания) для шапки.
2. `GET /emc/service-visits/:id/medical-documents` (`:id = emc_visit_id`) — список документов визита.
3. `POST /edm/documents` + `POST /emc/service-visits/:id/medical-documents` — создание и привязка документа (`EMCModule.md` §9.5).
4. `POST /emc/patients/:id/files` (`medical_document_id`) — файлы-приложения к документу (`EMCModule.md` §9.7).

### Роли и права

1. `EMC_PATIENT_GET` — просмотр клинических данных пациента.
2. `EMC_MEDICAL_DOCUMENT_GET` — просмотр списка документов.
3. `EMC_MEDICAL_DOCUMENT_CREATE` — создание документа.
4. `EMC_MEDICAL_DOCUMENT_LINK_MANAGE` — привязка документа к визиту (внутренний шаг).
5. `EMC_PATIENT_FILE_MANAGE` — загрузка файлов-приложений.

## Acceptance criteria

1. Страница показывает контекст визита и клинические данные пациента, важные во время приёма.
2. Документооборот визита отображается тем же общим паттерном, что и в остальных модулях системы.
3. Создание медицинского документа доступно и автоматически привязывается к визиту.
4. Подписание документа переводит визит в `completed` независимо от роли подписанта.
5. Есть прямой переход в полную ЭМК пациента.
6. Все состояния (loading/empty/error/offline/permissions) реализованы согласно таблице выше.
