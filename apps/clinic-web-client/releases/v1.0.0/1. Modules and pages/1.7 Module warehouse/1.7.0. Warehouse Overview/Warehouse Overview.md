# 1.7.0 Warehouse Module — Обзор и навигация

## Спецификация модуля

* **Модуль:** Warehouse Module (склад)
* **Тип:** раздел внутренней админки клиники
* **Платформа:** веб-приложение медицинской системы

## Общие UI-паттерны

Зафиксированы один раз; страницы ссылаются на них без повторного описания. Базовые паттерны реестра/формы/массового выбора/контекстного меню/пустых состояний — идентичны `1.6.0. Overview` HR Module (не дублируются здесь дословно, см. там).

### Паттерн «Первичный документ склада»

Часть складских действий (подтверждение заказа на поставку, финализация приёмки, выдача по запросу на пополнение, завершение ревизии) может требовать привязки сопроводительного документа ЭДО. **Важное отличие от HR-модуля**: в HR документ прикладывается прямо в теле запроса, которым выполняется само движение (`primary_document` — часть, например, `DismissEmployeeDto`), а здесь — нет. Ни одна из четырёх гейтуемых DTO склада (`{ action: "confirm" }`, `{ action: "issue", items }`, `PATCH .../complete` и т.д. — `WarehouseModule.md` §12.4, §12.7, §12.9) не содержит поля для документа вообще. Привязка документа к действию — **отдельный, самостоятельный вызов** `POST /document-events` (`WarehouseModule.md` §4.22, §12.10), выполняемый до того, как пользователь нажимает саму кнопку действия, а не в рамках одной формы с ней.

Обязательность условна и определяется настройкой Management Module (`warehouse.primary_document_required`), а не отделом исполнителя, как в HR, — она либо включена для всей клиники, либо выключена для всех четырёх действий сразу.

**Шаг 1 — прикрепление (отдельное действие, доступно сразу, как только сущность существует в нужном для действия статусе):**

```
Карточка заказа (статус «Черновик»):

┌── Связанные документы ──────────────────────────────┐
│  (пусто — документ ещё не привязан)                  │
│                              [+ Прикрепить документ] │
└─────────────────────────────────────────────────────┘

              [Отменить]              [Подтвердить] (disabled, если
                                        документ обязателен и не привязан)
```

```
┌── Прикрепить документ ───────────────────────────┐
│  ◉ Создать новый   ○ Из шаблона                  │
│  ○ Загрузить файл  ○ Из входящих                 │
├───────────────────────────────────────────────────┤
│               [Отмена]        [Прикрепить]        │
└───────────────────────────────────────────────────┘
```

**Шаг 2 — само действие (отдельная кнопка, без документа в теле запроса):** «Подтвердить», «Завершить приёмку», «Выдать», «Завершить ревизию» вызывают свой обычный эндпоинт без каких-либо полей документа.

Правила:

* Если настройка `warehouse.primary_document_required` выключена — кнопка действия доступна и применяет эффект сразу; блок «Прикрепить документ» можно не показывать вовсе (либо показывать не обязательным — решение на усмотрение дизайна, бэкенд его в этом случае игнорирует).
* Если включена — кнопка действия **неактивна**, пока к сущности не привязан хотя бы один документ через «Прикрепить документ» (клиентская защита; сама кнопка действия не проверяет наличие документа на сервере — она либо выполнит эффект, либо, если гейт не пройден, вернёт `deferred: true`, см. ниже).
* Привязка документа **не означает**, что действие уже применилось — нажатие «Подтвердить»/«Выдать»/«Завершить» после привязки может как применить эффект сразу (`deferred: false`, если документ не требует подписания или подписание уже произошло), так и оставить действие ожидающим (`deferred: true`, `EDMModule.md` §3.9) — во втором случае повторный клик не нужен: применение произойдёт автоматически по факту подписания, см. паттерн «Связанные документы» ниже.

### Паттерн «Связанные документы» (отложенные складские действия)

Аналог одноимённого паттерна HR Module (`1.6.0. Overview`), но источник — `warehouse_document_events` (`WarehouseModule.md` §4.22, §12.10), а не `hr_document_events`. На страницах заказов на поставку, приёмки, запросов на пополнение и ревизий под шапкой сущности показывается блок со списком привязанных документов и статусом действия:

```
┌── Связанные документы ──────────────────────────────┐
│  📄 Накладная-основание                              │
│     ● Ожидает подписания              [Открыть →]   │
└───────────────────────────────────────────────────────┘
```

Три состояния (та же цветовая семантика, что и в HR): **Ожидает подписания** (жёлтый), **Применено** (зелёный), **Отменено** (серый). Клик — карточка документа (модуль 1.5). Блок скрыт при отсутствии связанных движений.

### Паттерн «Списание по FIFO» (партия с ближайшим сроком годности — первой)

Общий для всего модуля принцип, зафиксированный один раз здесь и применяемый на `1.7.4`/`1.7.5`/`1.7.6`/`1.7.7` без повторного описания: когда операция расходует остаток товара (резервирование под услугу, реализация, выдача при пополнении потребительского склада), **партию выбирает система автоматически** — всегда сначала та, у которой `expiry_date` ближе (FIFO); партии в статусе `expired` в выбор не попадают. Оператор не выбирает партию вручную ни в одном из этих сценариев — единственное исключение — ручное списание (`1.7.5`), где кладовщик обязан указать конкретную партию явно (например, обнаружил порчу упаковки одной конкретной партии, а не общий расход).

**Это должно быть видно оператору, а не быть скрытой логикой бэкенда** — везде, где показывается остаток или результат расходной операции, интерфейс обязан явно показать, из какой партии (или партий, если одной не хватило) физически списано/зарезервировано/выдано количество, и её срок годности. Конкретные места:

* `1.7.5. Stock & Batches Page` — список остатков по партиям всегда отсортирован по сроку годности по возрастанию (ближайшая партия — первой строкой), это наглядно показывает порядок будущего списания.
* `1.7.6. Storages Page` — карточка склада при раскрытии товара показывает разбивку остатка по партиям с датами, а не только суммарное число.
* `1.7.7. Storage Requests Page` — после выдачи запроса на пополнение показывается, из каких партий фактически списано (`issued_batches`, `WarehouseModule.md` §12.7).
* Карточка ТМЦ/расходников в модулях «Мед. сестра» / «Врач» (`1.11.3`/`1.13.2. Department Warehouse`), где отображается результат резервирования расходников услуги — краткая подпись под позицией «Списано из партии {серия}, годен до {дата}» (см. эти документы).

### Статус-бейджи

| Семантика | Где используется | Цвет |
|-----------|------------------|------|
| Активно / в порядке | Товар активен, склад активен, партия `active`, поставщик `active` | Зелёный |
| В процессе / внимание | Заказ `confirmed`/не отгружен, приёмка `in_progress`, запрос `in_progress`, партия близка к истечению срока (≤30 дней) | Жёлтый/янтарный |
| Критично | Партия `expired`, долг поставщика `open`, ревизия с расхождением | Красный |
| Нейтрально / неактивно | Поставщик `suspended`, товар неактивен, партия `closed` (полностью израсходована/списана), заказ `canceled` | Серый |

### Права доступа — общий принцип

Видимость и доступность элементов интерфейса определяется набором прав пользователя из диапазона `WAREHOUSE_*` (`WarehouseModule.md` §9): право на просмотр раздела скрывает/показывает сам раздел, право на управление — интерактивные элементы внутри него. Полная сводная таблица — во frontend-документе `1.7.0. Overview` (Frontend).

## Acceptance criteria — общие (для всех экранов модуля)

* Навигация Warehouse содержит 8 активных пунктов (Поставщики, Каталог товаров, Заказы на поставку, Реестр маркировки, Склады, Запросы на пополнение, ТМЦ, Ревизии); Приёмка — вложенный экран, не пункт меню.
* Все реестры поддерживают поиск/фильтрацию/пагинацию и состояния пусто/загрузка/ошибка.
* Статус-бейджи во всех разделах используют единую цветовую семантику модуля.
* Действия, гейтуемые сопроводительным документом (подтверждение заказа, финализация приёмки, выдача по запросу, завершение ревизии), корректно ведут себя в обоих случаях настройки (документ обязателен/не обязателен) и показывают блок «Связанные документы» при инициированном, но не применённом действии.
* Элементы без прав скрыты или disabled с tooltip «Недостаточно прав».
