# 1.8.1. POS Page

## Спецификация страницы интерфейса

- Страница: Рабочий стол кассира (приём оплаты)
- Модуль: Касса (Cash Register)
- Позиция в модуле: Главная рабочая страница — доступна только при открытой смене (см. `1.8.0`)
- Тип страницы: Транзакционная (POS)
- Основные роли: Кассир, старший кассир
- Статус документа: Draft
- Связанная бэкенд-документация: `PaymentsModule.md` §4.1–4.2, §5, §7 (сценарии 1–4), §8; `CashRegisterModule.md` §4.2 (активная смена), §8

## Назначение страницы и сценарии использования

Главный экран модуля — классический POS-интерфейс: поиск счёта → выбор позиций к оплате → выбор метода оплаты → проведение платежа → чек. Экран доступен только в рамках открытой смены; при отсутствии смены — редирект на `1.8.0`.

Ключевые задачи страницы:

1. Найти счёт пациента (по счёту целиком либо визиту/пациенту).
2. Просмотреть позиции счёта с ценами и статусами.
3. Выбрать позиции к оплате (весь счёт либо частично).
4. Провести оплату одним из методов, включая комбинированную оплату.
5. Провести оплату через интернет-эквайринг (QR/ссылка для пациента) без непосредственного ввода данных карты кассиром.
6. Распечатать/показать чек об оплате.
7. Оформить возврат по ранее проведённой оплате.
8. Видеть контекст текущей смены и быстрый доступ к её управлению.

## User Flows / Task Flows для страницы

### Flow 1. Поиск и выбор счёта

1. Кассир вводит в поиск ФИО/MRN/телефон пациента, либо номер визита, либо сканирует QR-код визита (если есть, по аналогии с регистратурой).
2. Система показывает список счетов, соответствующих поиску (`GET /invoices` с фильтром) — приоритет счетам в статусе `draft`/`partially_paid` (требующим оплаты).
3. Кассир выбирает нужный счёт — открывается панель счёта (правая часть экрана либо отдельная область, без перехода на новую страницу).

### Flow 2. Приём оплаты по счёту целиком

1. В панели счёта отображаются все позиции; по умолчанию выбраны (отмечены) все неоплаченные (`draft`) позиции.
2. Кассир видит итоговую сумму к оплате.
3. Выбирает метод оплаты: Наличные / Терминал / Payme / Click / Uzum / Комбинированная.
4. Для наличных — вводит полученную сумму, система вычисляет сдачу.
5. Для комбинированной — разбивает итоговую сумму на несколько методов (сумма разбивки должна совпадать с итогом).
6. Нажимает **«Провести оплату»** → `POST /invoices/:id/pay`.
7. При успехе — экран чека (Flow 5).

### Flow 3. Частичная оплата (по выбранным позициям)

1. Кассир снимает отметки с части позиций (либо изначально включает режим «Оплатить частично»).
2. Итоговая сумма пересчитывается по оставшимся выбранным позициям.
3. Дальше — тот же процесс оплаты, что и Flow 2, с `payments_items`, указывающими выбранные позиции.
4. После оплаты статус счёта — `partially_paid`, если остались неоплаченные позиции; панель счёта остаётся открытой для последующей оплаты остатка.

### Flow 4. Оплата через интернет-эквайринг

1. Кассир выбирает метод Payme/Click/Uzum.
2. Система инициирует платёжную сессию (`POST /gateway/:provider/initiate`) и показывает QR-код/ссылку на экране, повёрнутом к пациенту (если есть второй монитор) либо в модали.
3. Пока пациент оплачивает на своём устройстве, экран кассира показывает статус **«Ожидание оплаты…»** с индикатором и периодическим опросом (`GET /gateway/transactions/:id`).
4. При `succeeded` — экран автоматически переходит к чеку (Flow 5); при `failed`/`canceled` — сообщение с возможностью повторить или выбрать другой метод; при затянувшемся `pending` — кнопка «Отменить и выбрать другой метод».

### Flow 5. Чек об оплате

1. После успешной оплаты — экран/модаль чека: позиции, суммы, метод оплаты, дата/время, кассир, касса, номер счёта.
2. Кнопка **«Печать чека»** — открывает системное окно печати (аналогично печати соглашения ПДн в регистратуре), рассчитанное на чековый принтер рабочего места.
3. Кнопка **«Готово»** — закрывает чек и возвращает на экран поиска (Flow 1) для следующего пациента.
4. Если счёт оплачен не полностью (частичная оплата) — на экране чека отдельно показывается остаток к оплате.

### Flow 6. Возврат оплаты (Refund)

1. В панели счёта — вкладка/раздел **«История оплат»**, список ранее проведённых `payments` по этому счёту.
2. Кассир выбирает оплату (или отдельные позиции внутри неё) и нажимает **«Оформить возврат»**.
3. Модаль подтверждения: сумма возврата, метод (по умолчанию — тот же метод, что и исходная оплата), предупреждение, если расходники по услуге уже списаны («Возврат не затронет складские остатки — услуга уже оказана»).
4. Подтверждение → `POST /payments/:id/refund`.
5. При успехе — toast «Возврат оформлен», статус позиции/счёта обновляется на `refunded`, доступна печать документа о возврате (тот же паттерн чека, Flow 5).
6. Возврат по счёту, все позиции которого уже возвращены — кнопка «Оформить возврат» скрывается для этого счёта.

Общий layout страницы:

1. Слева: Sidebar в свёрнутом состоянии.
2. Сверху: **Page Header** — название кассы, текущая смена (номер/время открытия), кассир; кнопки «Передать смену», «Закрыть смену», «X-отчёт» (переиспользуют логику `1.8.2`).
3. Основная область — двухколоночный layout: слева поиск/список счетов, справа — панель выбранного счёта (детали, оплата, история, возврат).

## Структура: Wireframes

### Левая колонка — поиск счетов

- Поле поиска (ФИО/MRN/телефон/номер визита) с debounce.
- Список найденных счетов: пациент, визит, сумма, статус (бейдж), дата создания.
- Быстрый фильтр «Только неоплаченные» (по умолчанию включён).

### Правая колонка — панель счёта

- Заголовок: пациент, номер визита, статус счёта.
- Таблица позиций: чекбокс, наименование, цена, количество, сумма, статус позиции (бейдж draft/paid/canceled/refunded).
- Итого к оплате (пересчитывается по отмеченным позициям).
- Блок выбора метода оплаты: сегментированный контрол (Наличные/Терминал/Payme/Click/Uzum/Комбинированная).
  - Наличные — поле «Получено» + вычисленная «Сдача».
  - Комбинированная — список строк «метод + сумма», кнопка «+ добавить метод», валидация суммы по разбивке.
- Кнопка **«Провести оплату»** — большая, основной акцент экрана.
- Вкладка/аккордеон «История оплат» — список `payments` с методом, суммой, статусом, кнопкой «Возврат» на каждой успешной записи.

### Модаль эквайринга (Flow 4)

- QR-код/ссылка крупным планом.
- Статус ожидания (спиннер + текст).
- Кнопка «Отменить».

### Экран/модаль чека (Flow 5)

- Логотип/название клиники, номер чека, дата/время, кассир, касса.
- Список оплаченных позиций и сумм.
- Метод оплаты, сумма, сдача (для наличных).
- Кнопки «Печать чека» / «Готово».

## Визуал: High-Fidelity mockups

Визуальные правила:

1. Крупная типографика для итоговой суммы к оплате — это центральный элемент экрана.
2. Кнопка «Провести оплату» — заметно крупнее и контрастнее остальных, disabled до выбора метода и суммы.
3. Статусы позиций/счетов — те же бейджи, что и в остальной системе (зелёный paid, серый canceled, красный refunded, жёлтый draft/partially_paid).
4. QR-код эквайринга — центрирован, минимум визуального шума вокруг.
5. Экран чека стилизован под печатную ленту (узкая колонка по центру), чтобы визуально соответствовать печатному результату.

Визуальные компоненты, обязательные к отрисовке в mockups:

1. Header с контекстом смены.
2. Список найденных счетов (пустой/с результатами).
3. Панель счёта с позициями и выбором метода оплаты (наличные, комбинированная).
4. Модаль эквайринга (ожидание / успех / ошибка).
5. Экран чека.
6. Вкладка «История оплат» с кнопкой возврата.
7. Модаль подтверждения возврата.
8. Состояние «Нет активной смены» (защитный редирект — состояние на случай прямого захода по URL).
9. Состояние loading/empty/error поиска счетов.

## Состояния и edge cases

| Состояние | Ожидаемое поведение |
|---|---|
| loading | Skeleton списка счетов; панель счёта — skeleton при выборе |
| empty | Поиск не дал результатов — «Счета не найдены», подсказка проверить номер/ФИО |
| error | Ошибка загрузки/оплаты — сообщение + «Повторить», сумма и выбранные позиции не сбрасываются |
| offline | Приём оплаты (в т.ч. наличными) заблокирован полностью — POS не должен работать в offline-режиме без сети, слишком высокая цена ошибки |
| permissions | Без `PAYMENTS_PAYMENT_CREATE` — кнопка «Провести оплату» скрыта, экран доступен только на просмотр; без `PAYMENTS_PAYMENT_REFUND` — кнопки возврата скрыты |

### Edge cases

1. Счёт уже полностью оплачен другим кассиром/каналом (личный кабинет пациента) между открытием панели и попыткой оплаты — `409`/конфликт статуса, панель обновляется, оплата блокируется с сообщением «Счёт уже оплачен».
2. Сумма разбивки комбинированной оплаты не совпадает с итогом — инлайн-ошибка, кнопка «Провести оплату» задизейблена до исправления.
3. Полученная сумма наличных меньше суммы к оплате — блокировка (не может быть отрицательной сдачи).
4. Смена закрылась (истекла/закрыта с другого места) во время работы на экране — модаль «Смена закрыта» с блокировкой дальнейших действий и редиректом на `1.8.0`.
5. Эквайринг завис в `pending` дольше разумного времени (например, 2 минуты) — предложение отменить и попробовать другой метод, без бесконечного ожидания.
6. Повторный webhook от провайдера (идемпотентность) — обрабатывается бэкендом (`PaymentsModule.md` §10), фронтенд просто получает финальный статус один раз.
7. Возврат позиции, расходники которой уже списаны — предупреждение в модали подтверждения (Flow 6, п. 3), возврат всё равно возможен (это финансовая операция, склад не затрагивается).
8. Попытка оформить возврат на сумму, превышающую исходный платёж — блокировка на клиенте, сервер также не должен это допустить.
9. Печать чека недоступна (принтер не подключён) — чек всё равно доступен на экране, кнопка печати просто выдаёт системную ошибку ОС/браузера, не блокирует завершение операции.

## Interaction & Animation

1. Выбор счёта из списка — плавное появление панели справа (slide-in, 250ms).
2. Пересчёт итоговой суммы при изменении отмеченных позиций — мгновенно, без анимации задержки.
3. Переход к экрану чека после успешной оплаты — fade-транзишн, 300ms.
4. Ожидание эквайринга — пульсирующий индикатор (не блокирующий спиннер на весь экран — кассир может свернуть модаль и работать с другим счётом, вернувшись позже).
5. Toast об успехе/ошибке — стандартный паттерн системы (slide-up, автоскрытие 3с), кроме критичных ошибок (смена закрыта), которые остаются модально до явного действия.

## Зависимости и ограничения

### API

1. `GET /payments/invoices` → фактически `GET /invoices` (`PaymentsModule.md` §8) — поиск и список счетов.
2. `GET /invoices/:id` — детали счёта.
3. `POST /invoices/:id/pay` — оплата (целиком/частично).
4. `GET /payments` — история оплат по счёту (фильтр `invoice_id`).
5. `POST /payments/:id/refund` — возврат.
6. `POST /gateway/:provider/initiate`, `GET /gateway/transactions/:id` — эквайринг.
7. Активная смена кассира — контекст берётся из `1.8.0`/глобального состояния модуля, не запрашивается заново на этой странице.

### Роли и права

1. `PAYMENTS_INVOICE_GET` — просмотр счетов.
2. `PAYMENTS_PAYMENT_CREATE` — приём оплаты.
3. `PAYMENTS_PAYMENT_GET` — просмотр истории оплат.
4. `PAYMENTS_PAYMENT_REFUND` — возврат.
5. `WORK_SHIFT_GET`/наличие активной смены — доступ к странице в принципе.

### Технические ограничения

1. Опрос статуса эквайринга — не чаще, чем раз в 2–3 секунды, с ограничением по времени (см. edge case 5).
2. Печать чека — нативная печать браузера/ОС, без шаблонизации через Documents Templates Module (чек не подписываемый юридический документ, а транзакционная квитанция).

## Acceptance criteria

1. Страница недоступна без активной открытой смены — редирект на `1.8.0`.
2. Поиск счёта работает по ФИО/MRN/телефону/номеру визита с debounce.
3. Панель счёта показывает все позиции с корректными статусами и пересчитываемой суммой к оплате.
4. Оплата возможна как по всему счёту, так и по выбранным позициям.
5. Комбинированная оплата валидирует совпадение суммы разбивки с итогом до отправки на сервер.
6. Оплата наличными корректно вычисляет сдачу.
7. Оплата через эквайринг показывает QR/ссылку и автоматически завершает флоу при успехе провайдера.
8. После успешной оплаты доступен чек с печатью.
9. Возврат доступен по каждой успешной оплате отдельно, с предупреждением о списанных расходниках при необходимости.
10. Все состояния (loading/empty/error/offline/permissions) реализованы согласно таблице выше.
